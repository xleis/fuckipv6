## 1. 背景与问题

当前项目已经具备单一 `fuckipv6` 节点程序、TUN 组网、P2P/Relay、Exit、Coordinator、安全会话和基础控制能力，但 GPUI 与 WebUI 仍呈现为后端模块的拼装界面：

- 导航和页面按实现模块划分，而不是按用户任务和节点状态组织；
- “翻墙”被错误地放在产品中心，而它不是所有用户都需要的能力；
- GPUI 与 WebUI 在信息架构、状态语义和操作流程上存在分叉；
- 部分 UI 动作没有真实后端闭环，按钮可能只返回 `Unavailable`；
- 文件共享、自动 Coordinator 接管、统一流量策略、分组权限等产品能力尚未形成完整体验；
- 旧 11 页 manifest、独立 WebUI 页面和嵌入式统一 WebUI 不能继续作为新设计基线。

本次重构不是给现有 UI 换皮，而是以“节点身份、网络成员关系、节点能力、用户任务”重新推导产品，再统一控制面、命令模型、状态模型、交互规范和渲染实现。

## 2. 产品目标

1. 建立唯一、长期运行、可被不同控制台连接的节点运行时。
2. 让 GPUI、WebUI 和 Android 共享同一领域模型、命令语义、权限判断、状态机、错误码和活动审计。
3. 将网络组网作为产品主体，而不是将代理或翻墙作为全局中心。
4. 覆盖同一个二进制内的所有节点能力：Coordinator、Relay、Exit、File。
5. 做成可长期运行的公网基础设施产品，而不仅是开发调试工具。
6. 第一版完整支持简体中文和英文，以及键盘、屏幕阅读器和高 DPI 显示。
7. 允许成熟 UI 组件复用，但保持统一产品外观和可预测交互。

## 3. 不可破坏的产品原则

### 3.1 只有一个节点身份

- 产品层只存在“节点”这一种身份。
- 不区分客户端节点、服务端节点、Relay 节点或 Exit 节点等产品类型。
- Coordinator、Relay、Exit、File 是节点在某个网络中的能力，不是另一种程序或身份。
- 普通成员不启用额外能力，节点能力环保持中性色。

### 3.2 每个节点身份平等

- 任意节点都可以加入零个、一个或多个网络。
- 节点可以在不同网络中承担不同角色和能力。
- 托管 Coordinator、拥有较高带宽或具有公网地址，不会使节点成为其他节点的主人。
- 网络管理员是网络范围内的治理身份，不等于节点所有者，也不自动拥有其他节点的机器权限。

### 3.3 翻墙不是产品中心

- 不设置全局“翻墙”一级入口或永久主开关。
- 互联网出口是“节点加入网络、网络提供 Exit 能力、节点选择路径、流量规则命中出口”的组合场景。
- 完全不使用 Exit 的用户仍能完整使用设备互联、Relay、Coordinator 和 File。

### 3.4 单二进制、多内部角色

- 桌面和服务器只发布一个 `fuckipv6` 可执行文件。
- 同一可执行文件可启动 `control` 与 `node` 两个内部进程角色。
- 进程数量不是产品形态；不得拆成产品意义上的客户端包和服务端包。
- Android 是平台安装包约束下的例外：APK + 共享 Rust 核心/JNI 库 + 前台 VpnService，但不得形成独立协议或产品身份。

### 3.5 后端是唯一事实来源

- UI 不得自行推断角色、能力、权限、最终路由或命令是否成功。
- 所有状态、权限、能力可用性和错误必须来自共享 Rust 领域模型或由其生成的契约。
- 可见控件必须有真实后端命令、状态回写、权限校验和测试覆盖。
- 未闭环能力不得显示为可点击控件；只能以明确的“不支持/未启用/当前环境不可用”说明出现。

## 4. 领域模型

```text
节点（全局身份）
└── 网络成员关系（0..N）
    ├── 网络内角色
    ├── 节点能力
    ├── Peer 与传输路径
    ├── 互联网出口策略
    ├── 安全与 File 权限
    └── 活动与状态
```

### 4.1 节点

节点拥有：

- 稳定的节点 ID 与密钥材料；
- 本机所有者身份；
- 设备名称、平台、版本和健康状态；
- 网络接口、TUN、覆盖地址和系统路由；
- 零到多个网络成员关系；
- 节点级统一流量规则；
- 本地诊断、审计和备份信息。

### 4.2 网络

网络拥有：

- 与域名、Coordinator 地址解耦的稳定签名网络 ID；
- 名称、用途、公开资料和可见性；
- 网络所有者、管理员和成员；
- 自定义组与动态组；
- 网络级安全、隐私、入口和出口治理策略；
- Coordinator 候选组和当前活动 Coordinator；
- 可选的 Coordinator、Relay、Exit、File 能力；
- 发现记录、活动和审计。

### 4.3 网络成员关系

一个成员关系至少包含：

- 所属网络；
- 节点引用；
- 网络内角色；
- 覆盖地址；
- 已启用的能力；
- 出口贡献/使用策略；
- 安全与 File 授权；
- 加入时间和状态；
- 最后在线、健康与活动信息。

### 4.4 身份分层

必须区分：

1. **节点所有者身份**：本机 Passkey 登录身份，拥有本机最高控制权。
2. **网络所有者身份**：网络范围内的最终授权身份，可离线保存、转让，不绑定某台节点。
3. **网络管理员身份**：网络作用域的可移植授权身份，可管理网络但不能自动控制成员机器。
4. **成员节点身份**：节点加入网络时使用的稳定密码学身份。

网络所有者/管理员凭据与节点所有者登录凭据必须完全分离。管理员通常从自己拥有的节点控制台进入网络，不能通过管理员角色登录别人的节点控制台。

## 5. 网络治理与角色

### 5.1 角色

- **网络所有者**：每个网络一个最高授权身份；可任命、暂停和撤销管理员，可转让所有权。
- **网络管理员**：可管理成员、审批加入、配置网络策略、共享能力、出口授权、隐私策略和审计。
- **普通成员**：使用被授权的网络资源，管理自己的节点和本地策略。

管理员权限不能覆盖节点所有者的本地拒绝或直接接管成员设备。管理员若需阻止不合规成员，应撤销其网络资源访问或将其移出网络。

### 5.2 所有者恢复

- 网络创建时建立管理员恢复阈值，例如 1-of-1、2-of-3。
- 所有者身份丢失时，必须达到阈值的管理员共同授权才能恢复或转移最高权限。
- 临时 Coordinator、单个管理员或单个节点不能自动继位为网络所有者。

### 5.3 自定义组与动态组

第一版支持：

- 以单个成员为授权对象；
- 自定义成员组；
- 动态组：所有成员、管理员、Exit 节点、File 节点等；
- 一个成员可属于多个组；
- 所有组策略、网络策略和节点本地策略共同生效；
- 权限冲突统一采用“拒绝优先”：任一适用策略拒绝即拒绝，只有所有适用的允许条件均满足才放行。

## 6. 节点服务生命周期与部署形态

### 6.1 control 与 node

内部角色必须分离：

- **control**：Passkey 会话、HTTPS/本地控制接口、证书、配置、审计、发现、操作编排，以及对 node 的启动/停止/重启。
- **node**：TUN、接口、Peer、路由、Coordinator、Relay、Exit、File 转移和数据转发。
- control 不要求 TUN/路由特权，node 不直接暴露公网 WebUI。
- 两者通过仅限本机、互相认证的 IPC 通信，共享同一命令与事件契约。

### 6.2 进程监督

- 由操作系统服务管理器长期托管，而不是由 UI 临时拉起。
- 桌面默认使用当前用户的服务；无头服务器使用系统服务。
- control 与 node 可被独立监督。
- control 异常退出时，node 继续转发；服务管理器重启 control，并重新读取 node 的真实状态。
- 停止 node 只停止数据面和网络职责，WebUI/GPUI 控制入口仍可使用。
- 关闭 GPUI、浏览器或退出桌面会话不得停止 control 或 node。
- 只有用户显式停止 node、node 异常退出或系统终止服务时，网络运行才会中断。

### 6.3 启动策略

- 图形会话默认启动 GPUI，并关闭 WebUI。
- 无头节点按配置启用 WebUI。
- 不得根据是否存在公网 IP 自动选择 UI；NAT、双栈、VPN 和动态地址都会使该判断不可靠。
- 桌面即使检测到公网地址，默认仍不开放 WebUI。
- 无头节点暂时没有公网地址也不会自动切换到 GPUI。
- 所有默认均可由显式配置覆盖。

### 6.4 Android

- 使用原生 Compose UI、前台 `VpnService` 和共享 Rust 节点核心。
- 关闭界面不等于停止网络；必须通过前台通知和显式停止操作管理。
- 使用 Android Credential Manager 管理 Passkey。
- 不使用公网 WebUI。
- 不限制节点能力；所有者在 Android 上也可启用 Coordinator、Relay、Exit、File。
- 平台必须显示电量、移动流量、后台限制和系统策略的真实风险；不得伪造可用性保证。
- Android 可使用系统文件选择器/SAF 选择 File 共享目录。
- 产品语义、术语、状态和操作顺序与桌面一致，但布局采用移动端模式。

## 7. 公网 WebUI 与所有者认证

### 7.1 公开范围

- WebUI 必须支持公网访问，面向无头服务器。
- 每个节点只允许一个所有者，不提供多账号、多租户或角色系统。
- 公网 WebUI 不通过 Relay 隧道暴露；无公网入口的个人电脑直接使用 GPUI。
- 节点可自行直接提供 HTTPS，也支持放在反向代理后。

### 7.2 安全要求

- 公网入口必须使用有效 HTTPS。
- 所有者远程登录只使用 Passkey/WebAuthn，不使用密码。
- 一个所有者可注册多个 Passkey 设备。
- 初始化时生成一次性恢复码；设备全部丢失后，只能在宿主机本地以系统权限重置。
- 启动时生成一次性初始化码，公网认领必须输入该码。
- 公网首次初始化前必须完成域名、证书或反向代理配置；禁止通过明文 HTTP 传输初始化码或执行认领。
- 未完成 HTTPS 时，只允许本地初始化，公网认领入口保持关闭。
- 支持防 CSRF、CSP、登录/命令限流、会话过期、可信代理、来源校验和审计。
- 高风险操作要求近期 Passkey 重新认证。

## 8. 网络发现与加入

### 8.1 可见性与加入模式

每个网络独立配置：

- 可见性：私有、仅邀请、公开可发现；
- 加入方式：开放加入、管理员审批；
- 审批模式：成员填写申请理由，管理员批准后加入；
- 开放模式：申请后立即通过，申请理由可选。

发现不等于可直接加入。公开网络资料只包含名称、用途、成员数、能力标签、出口政策、加入模式、管理员公开身份和隐私摘要，不公开成员真实地址、拓扑、路由和密钥。

### 8.2 发现索引

- 第一版提供项目默认公共发现索引，同时允许自建兼容索引。
- 索引只保存网络公开发布的签名元数据和当前 Coordinator 入口。
- 索引不掌握成员身份、密钥或管理权限，不是网络控制面。
- 索引不可用时，已加入的网络仍须正常运行。
- 网络使用稳定 ID 和签名记录防止冒名。
- 管理员可发布、修改、预览和下架公开卡片，并记录审计。

### 8.3 邀请

- 私有网络可通过管理员生成的限时邀请加入。
- 邀请绑定目标网络、有效期和使用次数。
- 接受邀请前必须展示加入模式、出口贡献要求、隐私策略和管理员权限。

## 9. Coordinator 与自动故障接管

### 9.1 网络身份与 Coordinator 解耦

- 网络身份由稳定签名 ID 表示，不以 Coordinator 域名或某台机器为身份。
- Coordinator 是当前在线的协调服务，可由成员节点或专用成员提供。
- 更换 Coordinator 不改变网络 ID。
- 托管 Coordinator 的节点不因此获得网络所有权。
- 第一版同一时刻只有一个活动 Coordinator Leader；候选节点通过共识避免脑裂。

### 9.2 候选组

- 管理员预先授权 Coordinator 候选组。
- 候选节点必须具备 Coordinator 能力、当前在线，并能通过公网或 Relay 被成员访问。
- 正常故障接管须取得候选组多数确认。
- control plane 故障不直接中断数据面；已建立 Peer、Relay 和 Exit 连接继续工作。
- 节点使用最后签名且未过期的网络策略；策略到期后必须失败关闭。
- 管理员策略变更、成员管理和发现记录更新在无可用 Leader 时暂停。

### 9.3 紧急接管

- 全部正常候选组不可用时，须由网络内多数现有成员共同确认，才可从其他在线成员中紧急选举临时 Coordinator。
- 没有多数的分区不得产生 Coordinator。
- 临时 Coordinator 只有临时运行权限：维持 Peer 协调、发布入口、同步最后有效策略、处理现有连接。
- 临时 Coordinator 不得修改成员资格、网络所有者、管理员、安全策略、出口授权或密钥，也不得自行升级权限。
- 正式候选组恢复后，控制权回到正规 Leader。
- 候选组无法恢复时，只有达到管理员恢复阈值才能迁移完整管理权。

## 10. 节点能力

第一版节点能力固定为：

- Coordinator
- Relay
- Exit
- File

普通成员使用中性色，不占能力环分段。能力注册表必须可扩展，后续新增能力无需重画所有页面。

### 10.1 Exit 治理

网络管理员可以：

- 声明节点自主决定是否贡献 Exit；
- 声明加入网络即要求贡献 Exit，成员加入前必须知情并接受；
- 指定部分节点为 Exit 或默认 Exit；
- 限制普通成员可选择的 Exit 集合；
- 将网络锁定到固定 Exit；
- 指定 Exit 白名单和故障策略。

加入时接受的强制贡献策略不能静默关闭；成员若不接受，只能退出网络。

每个成员关系有网络级默认 Exit。节点流量规则可指定“跟随网络默认 Exit”或管理员授权的具体 Exit。管理员锁定固定 Exit 时，规则级覆盖不可用。

最终可用 Exit 集合必须同时满足：

1. 节点具备并启用了 Exit 能力；
2. 节点或加入策略允许贡献；
3. 网络管理员授权；
4. 当前健康和可达。

Exit 不可用时必须失败关闭并明确报告，不能静默直连。

### 10.2 Relay

- Relay 与 Exit 是独立能力。
- 管理员可配置哪些成员可使用 Relay、哪些节点可提供 Relay，以及资源与配额。
- Relay 节点天然可见必要连接元数据，但不得将可见性扩展为内容或浏览历史。
- Relay 使用同样的小组成员、拒绝优先和本地不可绕过规则。

### 10.3 File

- Node 所有者选择共享目录和基础权限。
- 网络管理员可决定网络是否允许 File 能力及哪些成员/组可使用，但不能获得共享目录之外的文件访问权。
- 管理员身份不会自动获得共享目录内容的浏览或下载权限；需明确授权。
- 成员可浏览授权目录、上传、下载，支持 ACL、配额、断点续传和审计。
- 第一版不提供自动双向同步、目录实时镜像、冲突合并或系统级远程挂载。
- 所有浏览、上传、下载、拒绝和撤权操作进入活动审计。

## 11. 节点级流量路由

### 11.1 决策链

```text
流量
  → 节点统一流量策略：直连 / 进入指定网络 / 使用指定 Exit / 拒绝
  → 进入网络后：匹配 Peer 私网路径，或按网络出口策略选择 Exit
  → 直连：交给操作系统正常路由
```

“是否进入网络”属于节点级判断；“进入网络后使用哪个 Exit”属于网络能力和出口策略；两者必须分开。

### 11.2 规则匹配维度

第一版同时支持：

- 域名；
- IP / CIDR；
- 端口；
- 协议；
- 应用/进程。

进程匹配要求：

- 以节点上的可执行文件路径或平台应用身份（Bundle ID/包 ID）为规范身份；
- 显示名称只作标签；
- 子进程继承父应用匹配结果；
- WebUI 展示节点上的应用，而不是浏览器访问者所在设备上的应用；
- 无法可靠识别进程的流量必须标记为“未识别”，不得猜测归属；
- 平台无法可靠识别时，能力必须明确标记，而不是显示虚假的应用选择器。

### 11.3 规则语义

- 单一有序列表，从上到下首条命中即生效。
- 优先级只由用户显式排序决定，不使用不可见的“智能权重”。
- 同一规则内的不同条件按 AND 匹配。
- 同一条件内的多个值按 OR 匹配。
- 规则之间按顺序形成 OR 语义。
- 每个动作明确为：直连、进入网络、使用指定 Exit、拒绝。
- 列表底部必须存在明确的默认动作。
- 回环、链路本地、组播和系统安全所需路由由系统内置且不可被普通规则覆盖，但必须可见和可解释。
- 规则指定的网络或 Exit 不可用时失败关闭。
- 任何修改先显示受影响规则、最终路径和验证结果，再原子应用，并支持回滚。

### 11.4 规则编辑器

- 可视化有序规则表；
- 拖动排序；
- 行内显示启用状态、命中次数、最近命中和最终路径；
- 应用选择器读取节点实际应用/进程；
- 规则测试器允许选择应用、输入目标地址，展示 DNS/SNI 判断阶段、命中规则和最终路径；
- 高级视图主要用于完整配置查看、差异和导入，不作为主要编辑方式；
- 原始系统路由表不提供普通编辑入口，只在“节点 → 网络接口”中以只读方式诊断。

## 12. 安全策略

网络详情中的“安全策略”是统一编辑入口，能力页面只展示摘要和跳转。

统一策略模型：

- 主体：成员、自定义组、动态组；
- 资源：本机服务/端口、Exit 使用、Relay 使用、File 共享；
- 动作：允许或拒绝；
- 来源层：网络管理员策略、成员节点本地限制；
- 效果：所有适用层取交集，拒绝优先；
- 测试器：选择成员、资源和身份，显示最终结果及每条允许/拒绝来源；
- 编辑：条件表、批量编辑、差异预览、原子应用和回滚；
- File 目录内权限复用同一主体与组系统，不新建账号体系。

Node 所有者始终可以进一步限制本机暴露，网络管理员不能绕过本地拒绝。网络级拒绝也不能被本地允许覆盖。

## 13. 隐私与管理员可见性

“全局节点可见”仅指该网络内所有已认证成员可见，不包含公网游客或其他网络。

默认可见性：

- **网络成员可见**：显示名称、节点公钥、覆盖地址、在线状态、角色、能力状态、Peer 连通与质量。
- **仅网络管理员可见**：真实网络地址、出口使用明细、流量统计、配额、异常诊断和审计事件。
- **仅节点所有者可见**：本机应用/进程列表、本地分流命中、文件路径、密钥材料和本机详细日志。
- **任何角色均不可见**：私钥、Passkey 凭据和流量内容。

管理员可按数据类别配置隐私范围，但加入前必须展示当前策略，策略变化必须写入活动。Exit/Relay 因转发职责接触到的连接元数据不得被扩展成流量内容或浏览历史。

## 14. 信息架构

### 14.1 一级导航

1. 概览
2. 节点
3. 网络
4. 活动
5. 设置

桌面 GPUI 与 WebUI 使用左侧一级导航、顶部全局栏、页面内局部标签和右侧上下文详情面板。WebUI 窄屏收缩为顶部菜单；Android 使用底部导航，但术语、状态和操作顺序一致。

### 14.2 概览

固定层级：

1. 顶部：节点名称、唯一主状态、启动/停止或处理问题的主操作；
2. 中部：仅存在问题时显示“需要处理”，按影响排序，最多三条；
3. 网络区：紧凑网络卡片，包含能力、默认路径和主要异常；
4. 活动区：最近五条重要事件；
5. 快捷入口：创建网络、发现网络、加入网络。

不设置大型“翻墙开关”，不展示无行动价值的实时图表。

### 14.3 节点

固定标签：

- 运行状态；
- 流量路由；
- 网络接口；
- 身份与密钥；
- 诊断。

“运行状态”展示服务健康、版本、启动时间、监听状态和待处理异常；“网络接口”展示覆盖接口、TUN、地址、系统路由和冲突；“诊断”提供连通性测试、DNS/路由检查、日志摘要和诊断包。

### 14.4 网络

一级网络页包含两个主标签：

- **我的网络**：默认进入全局拓扑，可切换到列表；
- **发现网络**：浏览公开签名网络卡片、能力、加入方式、出口政策、隐私摘要及申请表单。

网络详情固定标签：

- 概览；
- 成员与拓扑；
- 安全策略；
- 活动。

动态标签仅在网络启用对应能力时出现：

- 互联网出口；
- Relay；
- Coordinator；
- File。

网络配置、自动化与路由能力声明放在概览管理区，不另设网络“设置”标签。节点级流量路由不复制到每个网络。

### 14.5 活动

活动只展示有用户意义的事件与变更，不展示原始运行日志。

记录范围：

- 网络创建、发布、加入、退出和管理员变更；
- Coordinator 选举、迁移、降级和恢复；
- Exit/Relay 能力启停、出口切换和策略失效；
- 路由、安全和证书记录变更；
- File 共享与文件操作；
- 连接异常、授权失败和需处理告警。

支持按网络、节点、严重程度、时间和类型筛选，并跳转到相关对象。公网 WebUI 默认脱敏真实地址、密钥和敏感路径。

原始 trace、包日志和内部错误栈只在“节点 → 诊断”中限时导出，不混入产品活动时间线。

### 14.6 设置

设置页只管理节点全局和控制面，不包含网络成员专属配置。采用“基础设置 + 可搜索高级设置 + 完整配置预览/差异导入”。

基础分组：

- 所有者与安全；
- 远程访问；
- 服务与更新；
- 发现索引；
- 数据与恢复。

高级设置覆盖：

- 精确监听地址、端口范围、接口白名单/黑名单；
- DNS 模式、DoH/DoT、DNS 泄漏保护和分流解析；
- NAT 穿透、Keepalive、路由优先级和并发限制；
- Exit、Relay、Coordinator 的默认资源上限、带宽配额、连接数和允许目标；
- WebUI 会话、并发、可信代理、限流、HSTS、来源策略和审计级别；
- 日志级别、保留周期、指标端点、远程日志和隐私脱敏；
- 更新通道、代理、签名校验、回滚和计划维护窗口；
- 新建网络的能力模板与默认安全策略；
- 完整配置查看、差异化导入和原子回滚。

### 14.7 状态展示

系统内部区分 control 连接状态与 node 运行状态，但 UI 只显示唯一主状态。

建议主状态：

- 未初始化；
- 已停止；
- 启动中 / 更新中 / 维护中；
- 运行正常；
- 运行降级；
- 节点运行故障；
- 控制服务异常。

优先级：

1. 用户意图或过渡状态；
2. 节点运行故障；
3. 运行降级；
4. 控制服务异常；
5. 运行正常。

状态区域可附一条可行动说明，但不并列显示“控制服务在线 · 节点降级”等双状态组合。只有不存在需要处理的问题时才显示“运行正常”。

## 15. 全局拓扑

### 15.1 基本表达

- “我的网络”默认进入直接绘制的全局拓扑。
- 所有网络在同一视图展示。
- 每个网络使用一种独立颜色和虚线边界圈出其成员范围。
- 网络边界颜色与能力颜色使用不同色板；能力颜色保持高可辨识度。
- 每个节点只绘制一次，不因加入多个网络而复制。
- 多网络节点位于成员范围的交叠区域；选中后显示所属网络、各网络角色和各项能力。
- 连接线继承所属网络颜色。
- 节点能力使用多色分段圆环 + 固定能力图标。
- 健康/故障/降级使用独立的角标，不覆盖能力颜色。
- 不展示真实地理位置或公网 IP；布局只表示逻辑连接和成员关系。

### 15.2 能力颜色

- Coordinator：紫色
- Relay：青色
- Exit：橙色
- File：绿色
- 普通成员：中性灰

分段环必须同时配固定图标，不能只靠颜色区分。一个节点承担多项能力时使用多段环，不产生多个节点副本。

### 15.3 布局

- 采用自动逻辑拓扑，由 Peer 连通关系和网络成员关系计算。
- 刷新后位置尽量稳定，不得每次全图跳动。
- 用户拖动节点可固定位置；“重置布局”恢复自动计算。
- 共享节点作为多个网络的视觉桥。
- 新节点和状态变化使用局部动画。

### 15.4 视图切换

- 拓扑与列表共享选中对象、筛选条件和批量选择。
- 列表用于搜索、排序、批量操作和可访问性。
- 点击拓扑节点打开右侧详情面板，不强制离开全局视图。
- 网络边界可以临时过滤或隐藏。
- 移动端默认列表，按需进入拓扑。

### 15.5 悬停

- 节点悬停：高亮所属网络边界与关联连接线；浮层显示名称、覆盖地址、单一主状态、网络角色和能力。
- 连线悬停：显示网络、路径类型、延迟/丢包和当前是否被使用。
- 悬停不得执行改变状态的操作。

### 15.6 右键菜单

菜单覆盖节点、连线、网络圈选区域和空白画布：

- 节点：查看详情、定位网络、复制覆盖地址、查看活动、固定布局、当前身份允许的节点操作。
- 网络边界：进入网络、只显示该网络、隐藏网络、查看网络活动。
- 连线：查看路径、诊断、查看活动。
- 空白：重置布局、适应窗口、切换图层、导出当前视图。

右键菜单可以包含允许的破坏性操作。用户已明确选择**立即执行，不弹额外确认框**：

- 破坏性操作放入菜单底部独立危险区；
- 菜单项直接写明后果；
- 不可逆操作显示危险图标和不可逆标识；
- 当前会话认证过期时先要求 Passkey 重新认证，通过后直接执行，不再弹确认；
- 可撤销操作执行后显示撤销入口和倒计时；
- 不可逆操作明确显示“无法撤销”并链接活动记录；
- 所有立即执行操作记录身份、时间、对象和影响范围；
- 权限不足的操作不显示；服务端仍须再次校验，不能信任旧 UI 状态。

右键菜单必须支持键盘菜单键；Android 使用长按等价交互。

### 15.7 多选与批量操作

- 单击选择；`Ctrl/Cmd` 切换选择；`Shift` 选择连续节点。
- 右键未选中对象时只作用于该对象；右键已选中对象时作用于整个选择集。
- 菜单标题显示影响对象数量。
- 根据选择集计算允许操作；存在无权限对象时必须明确说明受阻数量，不能静默跳过。
- 可撤销操作统一显示撤销入口；不可逆操作明确列出影响对象。
- 选择状态在拓扑和列表间保持同步。

### 15.8 规模与性能

第一版目标：

- 单个视图约 1,000 个节点；
- 约 5,000 条连接；
- 布局与筛选不阻塞主线程。

实现策略：

- 小规模使用 SVG/DOM 自定义节点，保留完整能力环、悬停和右键交互；
- 超过阈值自动切换 Canvas/WebGL 简化渲染，保留选择、搜索和筛选；
- 超过 1,000 个节点时按网络、成员组或逻辑簇聚合；
- 展开簇时按需加载；
- 布局计算放入 Worker 或共享 Rust/WASM 核心；
- 记录首屏时间、缩放帧率、选择延迟和内存上限作为验收指标。

## 17. 国际化与可访问性

### 17.1 国际化

- 第一版同时支持简体中文与英文；
- 支持跟随系统语言和手动切换；
- Rust 返回稳定错误码与结构化参数，不返回中文句子作为业务标识；
- GPUI、WebUI、Android 共用翻译键语义；
- 状态、命令、权限、空状态、危险操作、活动事件、错误和确认文本全部可翻译。

### 17.2 可访问性

- 键盘可完成所有核心操作；
- 焦点顺序、焦点环、快捷键和菜单键明确；
- 拓扑提供列表等价视图，屏幕阅读器读取节点名称、网络、角色、能力和唯一主状态；
- 颜色不作为唯一信息来源；
- 菜单、对话框、Tab、Tooltip 使用成熟的可访问性原语；
- 动画遵循减少动态效果的系统偏好；
- 目标为 WCAG 2.2 AA。

## 18. 控制面 API 与状态同步

### 18.1 协议

- HTTP/JSON 处理查询与命令；
- Server-Sent Events 推送操作结果、状态、拓扑差分和配置变化；
- 远程 WebUI 使用 HTTPS；
- GPUI 与本地控制使用 Unix Socket 或 Windows Named Pipe；
- 远程 HTTPS 和本地 IPC 共用命令、错误和状态语义，但使用不同的认证机制；
- 浏览器使用 Passkey 会话，本地 GPUI 使用操作系统用户身份和本地 IPC 认证。

### 18.2 命令生命周期

- 写命令返回 `operation_id`；
- UI 显示“执行中”，不得乐观声明成功；
- 只有收到 SSE 完成事件后才更新权威状态；
- 所有写操作带幂等键、权限校验和审计关联 ID；
- 命令失败必须返回结构化错误码、受影响对象和可恢复建议；
- 后台断线重连后重新拉取快照，再继续事件流，避免遗漏事件。

### 18.3 Schema

- OpenAPI/JSON Schema 由 Rust 领域模型生成；
- Rust 与 TypeScript 类型自动生成并纳入漂移检查；
- GPUI、WebUI、Android 共用命令枚举、状态机、错误码和能力判断；
- UI 契约测试必须验证所有可见动作都有后端处理。

## 19. 技术架构

### 19.1 Rust 核心

- 领域模型、权限、策略、状态机、命令和事件为唯一事实来源；
- control 与 node 来自同一个可执行文件；
- SQLite/WAL 保存控制状态、配置、审计和操作记录；
- 私钥、Passkey 关联秘密和恢复材料交给操作系统密钥存储或受保护文件；
- schema 版本化、事务迁移、失败回滚和备份。

### 19.2 GPUI

- 保留原生渲染；
- 不嵌入 WebView，避免性能和平台集成成本；
- 使用共享 Rust 模型、命令、错误、能力判断和设计令牌；
- 动态加载大页面和拓扑数据，避免一次性构造全部视图；
- 完整实现 IME、键盘导航、无障碍和平台菜单/文件选择。

### 19.3 WebUI

- React + TypeScript + Vite；
- Radix UI/Shadcn 作为菜单、对话框、Tabs、Tooltip、Popover 等行为与可访问性原语；
- TanStack Query 管理服务端状态和命令结果；
- TanStack Table/Virtual 处理成员、规则和活动等大数据列表；
- 允许复用其他成熟组件，但视觉、颜色、间距、字体和交互语义必须绑定共享设计令牌；
- 不整体套用 Ant Design/Material 等固定视觉主题；
- 拓扑、规则编辑器和 File 浏览器按需加载；
- 静态资源嵌入单一二进制，但保持独立前端源码和构建流程。

### 19.4 Android

- Kotlin + Jetpack Compose；
- 前台 VpnService 持有共享 Rust 节点核心；
- 原生 Passkey、通知、文件选择和后台限制集成；
- 底部五模块导航；
- 与桌面共享命令、事件、错误、状态、能力和翻译语义。

## 20. GPUI 与 WebUI 一致性

不将 GPUI 内容区替换为 WebView。性能优先，保留原生渲染。

两套 UI 必须共享：

- 功能模型、状态机、文案、权限判断和错误码；
- 设计令牌：颜色、间距、圆角、字号、控件尺寸和动效时长；
- 组件清单和交互语义；
- 键盘、右键、悬停和危险操作行为。

验收目标为“尽量一致”，不承诺跨渲染引擎逐像素相同：

- 同一信息架构和页面层级；
- 同一控件尺寸、布局顺序和状态文案；
- 同一平台、字体、窗口尺寸和 DPR 下进行并排截图与视觉回归；
- 可接受差异只包括字体栅格化、原生滚动条、IME 组合显示等平台细节；
- 不允许功能、权限、状态或操作流程分叉；
- Android 沿用同一产品语言，但使用移动布局，不纳入桌面像素比较。

## 23. 实施依赖顺序

第一版必须全部完成，但内部按依赖顺序实现：

1. **契约与模型**：冻结节点、网络、成员关系、角色、组、能力、策略、事件、操作和状态机；建立 OpenAPI/JSON Schema 与契约测试。
2. **控制面基础**：拆分 control/node，完成本地 IPC、HTTPS、Passkey、初始化码、SQLite/WAL、SSE、审计和进程监督。
3. **共享设计系统**：设计令牌、组件契约、i18n、可访问性、错误与空状态规范；建立 GPUI/WebUI 视觉基线。
4. **应用外壳与只读视图**：五个一级入口、节点页、网络发现/拓扑/列表、活动、设置及单一主状态。
5. **成员与治理**：网络创建、邀请、发现、开放/审批加入、所有者/管理员身份、组和隐私策略。
6. **流量与安全策略**：完整匹配维度、规则编辑器、测试器、统一 ACL、差异应用与回滚。
7. **Coordinator 与发现**：签名发现记录、候选组、正常选举、紧急临时 Coordinator 和管理员阈值恢复。
8. **Relay 与 Exit**：贡献策略、授权出口集合、默认/固定 Exit、失败关闭和活动审计。
9. **File**：共享目录、ACL、配额、浏览、上传/下载、断点续传和审计。
10. **Android**：Compose、前台 VpnService、Passkey、全部能力、移动布局和系统策略提示。
11. **平台硬化**：性能、安全、可访问性、国际化和网络端到端验收。
12. **发布门禁**：所有页面、命令、权限、状态、测试和文档完成后方可发布第一版。

每个功能按垂直切片完成：领域模型 → 后端命令 → 权限 → 事件/状态 → GPUI → WebUI → Android → 测试。任何阶段未闭环的能力只能显示明确说明，不能出现可点击伪控件。

## 27. 术语

- **节点**：全局设备身份及其本地运行时。
- **网络**：由稳定签名身份和成员关系组成的逻辑网络。
- **网络成员关系**：节点加入某网络后的角色、能力、策略和状态集合。
- **control**：管理控制面，负责认证、API、配置、审计和操作编排。
- **node**：网络运行时，负责 TUN、Peer、路由和实际数据转发。
- **网络所有者**：网络范围内最高授权身份。
- **网络管理员**：网络范围内被授权的治理身份。
- **节点所有者**：拥有并控制某台节点本机的身份。
- **能力**：节点在网络中可承担的 Coordinator、Relay、Exit、File 功能。
- **主状态**：UI 只向用户展示的一个最高优先级状态结论。
- **失败关闭**：指定路径或策略不可用时拒绝流量，而不是静默退化为直连或未授权路径。

## 29. 现状审计：为什么必须重构

### 29.1 审计基线

本节以当前工作区代码和 README 为事实来源，重点检查：

- `crates/client/src/gpui/view_model.rs`

审计结论不是对个人工作的评价，而是说明为什么继续在现有页面上叠功能无法得到统一、可产品化的结果。

### 29.2 当前 GPUI：manifest 驱动的垂直切片

当前 GPUI 使用固定的 11 页 `NodeUiManifest`：

1. `overview`
2. `networks`
3. `peers`
4. `topology`
5. `traffic`
6. `routing`
7. `exit_node`
8. `relay`
9. `logs`
10. `identity`
11. `settings`

它的优点是已经有共享 manifest、类型化动作、权限/可用性/后端状态字段，以及部分真实 `NodeSnapshot` 投影。它的问题同样明确：

- 页面按旧后端模块和开发阶段拆分，不是按“概览、节点、网络、活动、设置”的用户任务组织；
- Traffic、Peers、Topology、Routing 被拆成四个并列入口，把对象视图、诊断视图和配置视图混在同一层；
- Exit Node 与 Relay 被提升为全局能力页，File 不存在对应产品页面；
- 页面动作仍以表单堆叠为主，缺少完整对象详情、上下文面板和跨页状态；
- 原生 IME、无障碍、跨平台实机和正式视觉规范仍未完成；
- 当前 GPUI 的 `NativeNodeSession` 把 node runtime 放在 UI 进程生命周期内，并在窗口关闭/对象析构时提交 shutdown。这与目标“关闭 UI 不停止网络”直接冲突；
- 顶层 `--gpui` 已接原生入口，但部分命令子入口仍拒绝 GPUI，说明 UI 启动与长期节点服务尚未真正解耦。

因此 GPUI 可复用的是领域类型、命令总线、manifest 校验思想和部分快照投影；不可复用的是 11 页信息架构和 UI 持有 node 生命周期的模型。

### 29.3 当前 WebUI：两套表面并存

当前 WebUI 同时存在两个渲染面：

- 旧版统一控制页 `UNIFIED_MASTER_HTML`：在 `webui/mod.rs` 中以大型内嵌 HTML/CSS/JS 形式维护，使用独立页面、状态提取、请求和渲染逻辑；
- 节点 manifest 表面 `node_surface::NODE_MANIFEST_HTML` / `NODE_UI_JS`：在有节点适配器时使用 `/api/node/manifest`、`/api/node/snapshot` 和 `/api/node/commands`，按 manifest 提供另一套页面。

这不是“同一产品的两个主题”，而是两套控制面在同一个 HTTP 服务中的并存：

- 一套按旧 controller/API 工作；
- 一套按 NodeCommandBus/manifest 工作；
- 页面集合、状态来源、动作能力和前端实现均可能不同；
- 无节点适配器时回落到旧版，有节点适配器时切换到 manifest 表面；
- 旧版页面包含大量内嵌样式和脚本，难以与 GPUI 共享设计令牌、可访问性原语和视觉回归；
- 两套实现容易对同一动作给出不同可用性、确认和错误语义。

这正是“为什么启动后看到两个不同 UI、为什么长得不一样”的代码级原因。目标不是决定保留哪一套旧 UI，而是让二者都被新的统一信息架构和契约取代。

### 29.4 当前 UI 模式选择与目标不一致

当前 CLI 可区分：

- `--headless`：无桌面窗口，WebUI 服务继续监听；
- `--webui`：浏览器托管界面；
- `--gpui`：原生 GPUI；
- 无显式参数：进入自动模式。

当前自动模式仍受旧运行时兼容逻辑影响：部分命令子入口会走旧的浏览器托管适配器；顶层 GPUI 与命令子入口的启动路径也不完全一致。目标模型必须统一为：

- 有图形桌面会话：默认 GPUI，不因存在公网地址而改开 WebUI；
- 无桌面：默认按配置启用 WebUI；
- UI 类型由明确配置和平台能力决定，不由公网 IP 推断；
- 所有入口都连接同一长期运行 control/node，不在 UI 进程里另起一套节点生命周期。

### 29.5 当前能力与产品承诺的差距

| 能力 | 当前实际情况 | 目标状态 | 差距 |
|---|---|---|---|
| 单二进制 | 已收敛为单一 `fuckipv6` 入口，可承载多个内部角色 | 保持 | 入口已具备，进程生命周期和服务托管仍需统一 |
| Coordinator | 有协调、信令和多网络基础 | 自动候选组接管、紧急临时 Leader | 选举、多数确认、权限冻结和管理员恢复未产品化 |

| Exit | Linux 有内核转发/NAT 基础 | 统一治理、分流、失败关闭、质量验证 | 真实访问 Google、DNS、泄漏、恢复和跨平台未形成发布证据 |
| File | 有分块传输等基础设施 | 目录浏览、ACL、上传下载、断点续传 | 尚无完整用户流程和产品页面 |

| 公网控制面 | 远程 WebUI 依赖反向代理和旧 JWT/密码体系 | HTTPS + Passkey + 单所有者 + 初始化码 | 认证、初始化、安全头和会话模型均需重建 |
| 应用分流 | 有路由与部分进程识别基础 | 路径/平台应用 ID、子进程继承、不可识别标记 | 跨平台可靠性未知，UI 还没有完整测试器 |
| 自动发现 | 有网络发现目标 | 签名索引、开放/审批、申请理由 | 索引、签名记录和加入流程未完成 |
| 隐私治理 | 当前主要是基础状态可见性 | 成员/管理员/所有者分层字段权限 | 字段级策略、默认值和审计未实现 |

### 30.3 产品形态与 UI 选择

修正记录：

### 30.4 当前 UI 不合格，重构目标升级

用户明确指出现有 GPUI 与 WebUI 都存在产品化问题，且两条“只保留一个现有 UI”的路线都不能接受。确认：

- 重构不是换皮；
- 每个页面必须有真实功能闭环；
- 翻墙不是产品中心，每个节点能力平等；
- 先建立领域模型，再推导 UI；
- GPUI 与 WebUI 共享信息架构、状态、权限、错误和交互；
- 允许复用成熟 UI 组件，但不嵌入 WebView；
- 最终一致性目标从“像素级完全相同”修正为“同平台、同尺寸、同字体下尽量一致”，禁止功能分叉。

### 30.5 网络治理与成员关系

已确认：

- 节点是全局主体，可加入 0..N 个网络；
- 网络有一个所有者、多个管理员和普通成员；
- 支持自定义组和动态组；
- 权限冲突拒绝优先；
- 管理员有较强治理权，但不能直接控制成员机器；
- 节点本地所有者可以继续限制本机资源，不能绕过网络拒绝；
- 网络管理员可限制普通成员可选择的 Exit；
- 网络可要求加入即贡献 Exit，但必须在加入前明确告知；
- 网络可按节点自主贡献、管理员指定、默认接受、审批加入等模式治理。

### 30.6 概览、状态与设置

已确认：

- 概览是第一个 Tab；
- 概览只显示唯一主状态、需要处理的问题、紧凑网络摘要、最近活动和快捷入口；
- 没有要紧问题时只显示“运行正常”；
- 降级、节点故障、控制服务异常按优先级显示，不并列双状态；
- 设置需要更多可配置项；
- 高级设置可搜索，支持完整配置预览、差异导入和原子回滚；
- 基础设置与网络成员专属配置分离。

### 30.7 流量、路由与 Exit

已确认：

- 节点必须有统一流量判断：直连、进入网络、指定 Exit 或拒绝；
- 需要判断某流量是否走网络，而不是把一切都交给 Exit；
- 第一版同时支持域名、IP/CIDR、端口、协议、应用/进程；
- 规则有序、首条命中；规则内条件 AND，多值 OR；
- 应用以路径或平台应用 ID 为规范身份，子进程继承；
- 无法识别进程必须标记未知，不能猜测；
- 网络不可用或目标 Exit 不可用时失败关闭，不能静默直连；
- 管理员可设默认 Exit、授权集合、固定 Exit 和强制贡献；
- Relay 与 Exit 是独立能力；
- 网络级 ACL 与节点本地限制取交集。

### 30.8 发现、Coordinator 与加入

已确认：

- 第一版必须做网络发现；
- 默认公共索引，同时允许自建；
- 索引只保存签名公开元数据和 Coordinator 入口，不是控制面；
- 公开可发现不等于开放加入；
- 加入方式可开放或审批，可要求申请理由；
- 私有网络支持限时邀请；
- 网络身份与 Coordinator 地址解耦；
- 管理员预授权候选组，候选组正常故障时多数接管；
- 只有候选组全部不可用，才允许从其他在线成员紧急选举；
- 紧急 Leader 只获得临时运行权限，不能修改成员、管理员、策略、出口授权和密钥；
- 正式管理权迁移必须达到管理员阈值。

### 30.9 能力与第一版范围

已确认：

- 第一版节点能力为 Coordinator、Relay、Exit、File；
- 第一版全部支持，不发布只读静态页或伪按钮；
- File 第一版包含共享目录浏览、上传、下载、断点续传；
- File 不做同步、实时镜像和系统挂载；
- 管理员不会因角色自动获得 File 内容权限；
- Android 不限制节点能力，由所有者决定；
- Android 使用原生 Compose、共享 Rust 核心和前台 VpnService；
- 不存在现有用户，不实现旧配置、旧 CLI 产品或旧邀请票据兼容层。

### 30.10 拓扑与交互

已确认：

- 所有网络在同一全局拓扑中展示；
- 不同网络用不同颜色虚线圈出；
- 同一节点只绘制一次；
- 能力用多色分段圆环，并提供固定图标；
- 健康状态独立角标，不覆盖能力色；
- 拓扑与列表共享选中、筛选和批量操作；
- 支持悬停、右键、多选；
- 支持稳定布局、拖动固定和重置；
- 第一版目标约 1,000 节点、5,000 连接；
- 移动端默认列表，长按等价右键；
- 危险右键操作立即执行，不弹额外确认；会话过期先 Passkey 重认证，然后直接执行；
- 不可逆操作必须明确标识“无法撤销”并记录审计。

### 30.11 WebUI 安全与所有者模型

已确认：

- WebUI 面向公网，但仅供节点所有者一人使用；
- 不使用全局账号系统，不做多租户；
- 登录只使用 Passkey/WebAuthn；
- 一个所有者可注册多个 Passkey；
- 允许公网第一个访问者初始化，但必须输入启动时生成的一次性初始化码；
- 公网初始化前必须完成有效 HTTPS；
- 无 HTTPS 时只允许本地初始化，禁止 HTTP 降级；
- 全部 Passkey 丢失后，只能在宿主机本地以系统权限重置；
- 高风险操作要求近期 Passkey 重认证。

### 30.12 技术路线

已确认：

- Rust 领域模型和命令/事件契约是唯一事实来源；
- GPUI 原生渲染，不替换为 WebView；
- WebUI 使用 React + TypeScript + Vite；
- 允许成熟可访问性组件，但视觉由共享设计令牌控制；
- HTTP/JSON 命令 + SSE 权威事件；
- 写命令返回 operation ID，不能乐观成功；
- OpenAPI/JSON Schema 生成 Rust/TypeScript 类型；
- 简中和英文双语；
- UI 只显示有真实后端闭环的动作；
- 所有节点能力第一版全部交付后才发布。

### 30.13 修正与被否决的旧方向

| 旧方向 | 最终决定 | 原因 |
|---|---|---|
| WebUI 只监听回环 | 支持公网无头访问 | 无头服务器必须可远程管理 |
| 通过 Relay 暴露 WebUI | 不通过 Relay | 管理面不应依赖数据面，且扩大攻击面 |
| 根据公网 IP 选择 GPUI/WebUI | 根据桌面环境和显式配置 | 公网地址不能代表交互环境 |
| 两个现有 UI 中二选一 | 按新信息架构重写两者 | 两个都不合格，保留任意一个都会保留功能割裂 |
| GPUI 内嵌 WebView | 保留原生渲染 | 性能和平台集成成本不可接受 |
| GPUI/WebUI 像素级相同 | 尽量一致并做视觉回归 | 跨渲染引擎与原生字体无法保证逐像素 |
| 全局“翻墙”一级入口 | Exit 作为网络能力 | 不是所有用户都需要 Exit |
| 隐藏“智能优先级” | 显式有序规则和测试器 | 隐藏行为不可解释、不可审计 |
| 手动改系统路由作为产品流程 | 类型化路由策略由 node 应用 | 容易断网、难恢复、不可审计 |
| 手动迁移 Coordinator | 候选组自动多数接管 | 无公网节点也可能失去原 Coordinator |
| 初始化使用密码/HTTP | Passkey + 初始化码 + HTTPS | 公网首次认领攻击面过大 |
| 旧配置/旧 CLI 兼容 | 不兼容 | 无现有用户，兼容成本没有产品价值 |
| 未完成能力显示可点击按钮 | 显示明确不可用原因 | 伪功能破坏信任 |
| 静态页面作为第一版交付 | 每个动作完整闭环 | 产品不是演示稿 |

## 31. 被否决方案与原因

### 31.1 保留旧 WebUI，只换视觉

否决原因：

- 旧 WebUI 自带第二套状态和命令语义；
- 页面按旧后端模块划分，无法与新领域模型长期共存；
- 继续维护内嵌巨型 HTML/JS 会扩大安全、可访问性和一致性债务；
- 只换皮不能解决 UI 持有节点生命周期、错误语义和权限判断分叉。

### 31.2 用 WebView 统一 GPUI 与 WebUI

否决原因：

- 用户明确拒绝，性能消耗不可接受；
- 原生文件选择、网络接口、IME、快捷键和系统菜单会被 WebView 边界削弱；
- 相当于放弃 GPUI 的价值，却保留两套运行时开销；
- 不能证明跨平台性能和可访问性更好。

### 31.3 建立全局账号系统

否决原因：

- 产品是单所有者节点，不是 SaaS；
- 全局账号会成为新的身份根和攻击目标；
- 节点所有权、网络成员身份和网络治理身份是三个不同层次，不能用中心账号混同；
- 第一版没有多租户需求。

### 31.4 通过 Relay 暴露公网 WebUI

否决原因：

- Relay 故障会同时破坏数据面和管理面；
- 管理面被引入本不需要的网络路径；
- Relay 运营者可能接触管理流量；
- 增加认证、反代和公网攻击面；
- 无公网个人电脑已被明确要求直接使用 GPUI。

### 31.5 明文 HTTP 首次认领或短期降级

否决原因：

- 初始化码一旦在 HTTP 上传输即可被窃取；
- 首个访问者初始化机制本身存在竞争；
- 降级开关通常会被长期保留，等价于永久后门；
- 没有有效 HTTPS 时，本地初始化已经足够完成首次配置。

### 31.6 全局“翻墙”主开关

否决原因：

- Exit 是网络能力组合，不是所有网络的统一目标；
- 全局开关无法表达多网络、默认 Exit、固定 Exit 和规则覆盖；
- 会让设备互联、Relay、Coordinator、File 用户被无关功能干扰；
- 隐藏的全局覆盖会破坏有序规则的可解释性。

### 31.7 直接编辑系统路由表作为主产品流程

否决原因：

- 与 TUN、DNS、策略路由和网络切换存在竞态；
- 崩溃后可能留下断网状态；
- 无法统一审计、回滚和权限判断；
- 用户需要的是“这条流量怎么走”，不是“写一条 OS 路由”。

### 31.8 隐藏的“智能优先级”替代显式规则

否决原因：

- 用户无法解释命中原因；
- 管理员无法审查实际出口；
- 规则冲突无法测试；
- 变更后难以判断行为为何改变；
- 第一版要求可解释、可测试、可回滚。

### 31.9 让管理员自动拥有成员机器或 File 内容权限

否决原因：

- 网络治理权不等于设备所有权；
- 会破坏节点本地所有者的最终控制权；
- File 内容和本机进程信息属于高敏感数据；
- 管理员应通过明确策略获得网络范围权力，而不是隐式获得机器权力。

### 31.10 多 Leader 同时写入

否决原因：

- 会造成成员、策略、出口授权和审计分叉；
- 合并冲突无法可靠判定谁有最新权限；
- 数据面可多路径，但控制面写入必须单 Leader；
- 分区期间应暂停治理写入，而不是制造两个真相。

### 31.11 立即重写全部底层协议

否决原因：

- 当前协议栈、数据面和性能工作是可复用资产；
- 产品化阻塞点主要在控制面、生命周期、身份、UI 契约和验证；
- 全量重写会失去已有测试与性能基线；
- 正确顺序是先稳定边界，再逐步替换不满足契约的模块。

### 31.12 第一版先只做 UI，后端以后补

否决原因：

- 用户明确要求第一版全部支持；
- 静态页会制造虚假完成度；
- UI 交互设计只有在真实命令、权限和失败路径闭环后才有意义；
- 契约测试要求每个可见动作都有后端处理和状态回写。

### 31.13 为“以后可能有人用”保留兼容层

否决原因：

- 明确不存在现有用户；
- 兼容层会让旧页面、旧命令和旧身份模型继续污染新架构；
- schema 可以版本化，但不需要保留已否决的产品路径；
- 第一版应大胆清理，之后通过明确迁移机制演进。

## 32. 核心用户旅程

### 32.1 旅程约定

每个旅程都要求：

- 明确前置条件；
- 明确用户看到的主状态；
- 明确成功判据，不以“请求已发送”作为成功；
- 明确失败后的恢复路径；
- 产生用户可读活动记录；
- 测试覆盖加载、空、错误、无权限和中断恢复状态。

### 32.2 J-01：桌面首次启动与本地初始化

**前置条件**

- Linux/macOS/Windows 图形桌面；
- 已安装单一 `fuckipv6` 二进制；
- 当前用户具备创建 TUN/配置路由所需的系统授权；
- 首次运行，无 owner、Passkey 和网络配置。

**用户流程**

1. 启动 `fuckipv6`；
2. 系统检测到图形会话，启动 GPUI，不自动开放 WebUI；
3. 概览显示“未初始化”和唯一主操作“完成本机初始化”；
4. 应用生成本地初始化上下文和一次性初始化码；
5. 系统提示用户注册 Passkey；
6. Passkey 注册成功后，展示恢复码并强制用户确认已离线保存；
7. control 创建所有者记录、审计记录和初始配置；
8. node 以最小默认权限启动，概览切换到“运行正常”或明确的授权缺失状态。

**成功判据**

- owner 持久化成功；
- Passkey 可用于本机敏感操作；
- node 状态来自真实快照；
- WebUI 未被意外开放；
- 重启 control 后 owner 和 Passkey 关联仍存在。

**失败与恢复**

- Passkey 注册取消：保留“未初始化”，不创建半成品 owner；
- node 权限不足：control 可用，但概览显示节点启动故障和具体修复建议；
- 恢复码未确认：不得进入完成态；
- 初始化中断：下次启动从中断点继续，不能生成两个 owner。

### 32.3 J-02：无头服务器首次启动

**前置条件**

- 无图形桌面；
- 用户通过 SSH 或本地终端管理；
- 尚未配置域名、证书或 Passkey。

**用户流程**

1. 启动 `fuckipv6`；
2. 系统选择 headless/WebUI 模式，但公网认领入口保持关闭；
3. 本机回环 WebUI 可用，终端显示仅本机可访问的初始化入口；
4. 用户完成本地初始化并注册 Passkey；
5. 用户配置域名、证书或受信反向代理；
6. 系统验证 HTTPS 后开放公网 WebUI；
7. 用户从远程设备使用 Passkey 登录并确认唯一主状态。

**成功判据**

- 未完成 HTTPS 前公网不能访问初始化或管理 API；
- 拒绝任何 HTTP 明文认领降级；
- 证书验证失败时控制面明确报错且不开放公网；
- 本地初始化与远程登录进入同一 owner 记录。

### 32.4 J-03：公网首个访问者认领

**前置条件**

- 节点已配置有效 HTTPS；
- owner 尚未创建；
- 启动时已生成一次性初始化码；
- 公网入口开放首次认领。

**用户流程**

1. 所有者访问 HTTPS 地址；
2. 页面显示节点身份摘要、证书状态和“认领此节点”；
3. 所有者输入一次性初始化码；
4. 服务端校验码、来源限流和当前未初始化状态；
5. 所有者注册 Passkey；
6. 服务端原子提交 owner、Passkey 和审计记录；
7. 初始化码立即失效，公网认领入口永久关闭。

**成功判据**

- 并发首次认领只有一个事务成功；
- 初始化码只可用一次且不进入 URL、日志或分析系统；
- 失败次数触发限流和告警；
- 成功后只能通过新 Passkey 操作。

**失败与恢复**

- 初始化码泄漏：在完成认领前由本地系统权限重新生成；
- 已被人恶意认领：只能由宿主机本地系统权限执行恢复，不能通过公网“找回”；
- 证书错误：关闭公网认领，不提供跳过验证选项。

### 32.5 J-04：创建网络

**前置条件**

- 节点已初始化且 node 正在运行；
- 本机有可用监听端口；
- 用户有权在本机创建网络成员关系。

**用户流程**

1. 网络 → 我的网络 → 创建网络；
2. 输入网络名称、用途、可见性、加入模式、默认 Exit 策略；
3. 选择是否立即贡献 Coordinator、Relay、Exit、File；
4. 预览隐私影响和加入者将看到的信息；
5. 系统创建稳定网络 ID、成员关系、所有者身份和初始策略；
6. 若启用 Coordinator，启动候选服务并发布签名入口；
7. 页面进入网络概览，拓扑只绘制真实在线成员。

**成功判据**

- 网络 ID 与 Coordinator 地址解耦；
- 网络 owner 和管理员权限写入权威状态；
- 公开资料与私密资料分离；
- 失败时没有半创建网络或孤立密钥。

### 32.6 J-05：发现网络、申请并加入

**前置条件**

- 节点已初始化并在线；
- 发现索引可用或用户持有 Coordinator 入口；
- 目标网络允许发现和申请。

**用户流程**

1. 网络 → 发现网络；
2. 搜索或筛选网络；
3. 查看公开签名资料、能力、Exit 政策、隐私摘要和加入方式；
4. 选择“申请加入”；
5. 页面展示加入后必须接受的策略，包括强制 Exit 贡献和隐私范围；
6. 填写申请理由；
7. 提交后显示“等待审批”；
8. 管理员批准后，节点收到签名成员资格；
9. 节点拉取当前策略和 Coordinator 信息，建立 Peer 连接；
10. 拓扑显示新成员关系，活动记录加入结果。

**成功判据**

- 发现记录签名验证通过；
- 用户在接受前看到全部强制贡献条款；
- 审批前不能使用网络资源；
- 索引不可用不影响已加入网络。

**失败与恢复**

- 签名无效：拒绝展示为可加入；
- Coordinator 离线：显示最后验证时间和可重试状态；
- 申请被拒：允许查看原因（若有）并重新申请或选择其他网络；
- 用户不接受强制策略：允许取消，不创建成员关系。

### 32.7 J-06：通过邀请加入私有网络

**前置条件**

- 管理员有邀请权限；
- 目标网络为私有或仅邀请；
- 邀请包含稳定网络 ID、有效期和用途。

**用户流程**

1. 管理员生成限时、限次邀请；
2. 用户打开邀请；
3. 页面验证签名、网络 ID、有效期和剩余次数；
4. 展示加入模式、Exit 贡献要求和隐私策略；
5. 用户接受并提交加入；
6. 若为审批模式，管理员批准；
7. 成员关系生效，邀请次数原子扣减。

**成功判据**

- 邀请不能用于其他网络；
- 过期、撤销、耗尽或签名错误的邀请明确失败；
- 管理员无法看到用户未提交的本机信息。

### 32.8 J-07：选择 Exit 并验证可访问性

**前置条件**

- 节点已加入至少一个网络；
- 网络提供至少一个健康 Exit；
- 节点有权使用该 Exit；
- 已配置节点流量规则。

**用户流程**

1. 网络 → 互联网出口；
2. 查看默认 Exit、可用 Exit、延迟、丢包和策略限制；
3. 在节点 → 流量路由中选择“跟随网络默认 Exit”或管理员允许的具体 Exit；
4. 使用规则测试器确认目标流量命中 Exit；
5. 应用规则，等待 operation 完成事件；
6. 节点启用必要的 TUN/DNS/路由变更；
7. 从节点发起明确的 DNS、HTTPS 和 IPv4/IPv6 检查；
8. `https://www.google.com/` 返回有效 HTTPS 响应，页面内容可加载；
9. YouTube 等目标按测试口径验证；
10. 活动记录规则应用、出口选择和验证结果。

**成功判据**

- 流量确实经过目标 Exit，而不是出口节点本地直连；
- DNS 查询路径符合策略，不发生未授权泄漏；
- 目标不可达时失败关闭，不静默直连；
- 验证结果带时间、目标、出口和网络条件，不是单纯“绿灯”；
- 停止规则后系统路由和 DNS 恢复。

**失败与恢复**

- Exit 离线：保留失败关闭并提示切换；
- Exit 授权撤销：立即停止使用并记录活动；
- TUN/路由应用失败：回滚上一组有效规则；
- Google 不可达：报告出口、DNS、TCP/TLS 阶段，不笼统宣称“翻墙不可用”；
- 测试导致本机断网：隔离测试环境清理，不得要求用户手工 kill 进程作为正常恢复手段。

### 32.9 J-08：按域名和应用分流

**前置条件**

- 节点支持 TUN 和所选匹配维度；
- 用户可查看本机应用列表；
- 网络可用 Exit 或直连路径。

**用户流程**

1. 节点 → 流量路由 → 新建规则；
2. 设置流量方向、目标网络或直连、匹配条件；
3. 添加域名、IP/CIDR、端口、协议或应用；
4. 将规则插入有序列表；
5. 打开规则测试器，选择模拟目标/应用，查看首条命中和最终路径；
6. 预览差异并原子应用；
7. 在活动详情查看命中统计和失败关闭事件。

**成功判据**

- 规则优先级可见；
- 多值条件按 OR、同一规则条件按 AND；
- 子进程继承应用身份；
- 无法识别应用时显示“未识别”，不自动套用到错误规则；
- 平台不支持进程匹配时禁用该条件并解释原因；
- 回滚恢复应用前规则。

### 32.10 J-09：管理员要求加入即贡献 Exit

**前置条件**

- 网络 owner/管理员有策略权限；
- 节点加入前尚未接受该网络成员关系。

**用户流程**

1. 管理员在 Exit 治理中启用“加入即要求贡献 Exit”；
2. 配置允许的出发网络、带宽配额、目标和可撤销条件；
3. 系统在公开卡片和申请页显著展示该要求；
4. 成员在加入前确认接受；
5. 接受后成员关系生效，节点启用 Exit 能力；
6. 节点退出网络时同时撤销能力；
7. 管理员不能远程绕过节点本地资源限制或系统权限。

**成功判据**

- 未确认贡献要求的用户不能加入；
- 该要求不能被成员静默关闭；
- 节点平台不支持 Exit 时，加入流程在提交前明确阻止；
- 管理员变更贡献策略会通知受影响成员，并给出现有连接的失败关闭语义。

### 32.11 J-10：Exit 故障与网络失败关闭

**前置条件**

- 节点有一条规则使用指定 Exit；
- 该 Exit 中途离线、被撤权或策略失效。

**用户流程**

1. 数据面检测 Exit 不可用；
2. 节点立即停止沿该路径发送；
3. 规则要求失败关闭时拒绝流量，不回落直连；
4. 概览出现唯一主状态“运行降级”及受影响网络；
5. 活动记录时间、Exit、规则和受影响连接；
6. 若配置了管理员授权备用 Exit，用户可显式重试选择；
7. 路径恢复后重新验证，不自动假装成功。

**成功判据**

- 不产生未授权泄漏；
- 不残留黑洞路由导致整个主机关联网络失联；
- 用户可以识别是 DNS、Exit、Relay、TUN 还是策略问题；
- 恢复后活动记录闭环。

### 32.12 J-11：Coordinator 正常故障接管

**前置条件**

- 网络有预授权候选组；
- 存在多数候选可通信；
- 原 Leader 失效；
- 成员继续使用最后有效策略。

**用户流程**

1. 候选节点检测 Leader 失联；
2. 候选组按共识选出唯一新 Leader；
3. 新 Leader 验证自己持有最新签名状态；
4. 发布新入口和任期信息；
5. 成员验证签名并切换；
6. 数据面连接尽可能保持；
7. 活动记录故障、选举、任期和恢复。

**成功判据**

- 同一任期不存在两个可写 Leader；
- 没有多数候选时不产生新 Leader；
- 成员不会因入口变化改变网络身份；
- 控制面切换不无条件中断已建立数据面。

### 32.13 J-12：候选组全失与紧急临时 Leader

**前置条件**

- 全部正常候选组不可用；
- 网络内仍有多数在线成员；
- 治理写入必须继续被限制。

**用户流程**

1. 在线成员发起紧急接管提议；
2. 网络内多数确认提议；
3. 从在线成员中选出临时 Leader；
4. 临时 Leader 只同步最后有效策略、维持协调和发布入口；
5. UI 明确显示“临时运行权限”；
6. 成员/管理员/策略/Exit 授权/密钥的写操作全部禁用；
7. 正式候选恢复后交回；
8. 或达到管理员恢复阈值后，走独立的管理权迁移流程。

**成功判据**

- 无多数的分区不能选出临时 Leader；
- 临时 Leader 无法自我升级；
- 所有试图越权的命令返回结构化拒绝；
- 管理员阈值恢复有完整审计和多签证据。

### 32.14 J-13：File 共享与断点续传

**前置条件**

- 节点 owner 选择共享目录；
- 该节点在目标网络启用 File 能力；
- 网络策略和文件 ACL 均允许访问。

**用户流程**

1. 节点 owner 选择目录并配置配额、只读/读写、组授权；
2. 网络管理员检查网络是否允许 File 及可用成员范围；
3. 被授权成员打开网络 → File；
4. 浏览目录、查看权限和配额；
5. 上传或下载文件，中断后从已完成块继续；
6. 活动记录操作者、资源、结果和撤销；
7. owner 撤权后，新请求立即拒绝，已建立传输按策略终止。

**成功判据**

- 所有路径经过 canonicalize 和目录边界校验；
- 拒绝 `..`、绝对路径注入、符号链接逃逸和竞态替换；
- 管理员不因角色自动获得内容访问；
- 未授权成员看不到文件名、大小或目录结构；
- 配额和并发限制真实生效。

### 32.15 J-14：关闭 UI 后网络继续

**前置条件**

- 节点和网络正在运行；
- control/node 已由服务管理器托管。

**用户流程**

1. 用户关闭 GPUI 窗口或浏览器标签；
2. UI 进程退出；
3. control 与 node 保持运行；
4. 网络流量和 Exit/Relay 职责继续；
5. 重新打开 UI 时从持久化和当前快照恢复权威状态；
6. 不需要重新创建网络或重新输入 Passkey（会话策略允许时）。

**成功判据**

- 关闭 UI 不触发 node shutdown；
- 重新打开后显示真实运行时间，而不是 UI 启动时间；
- 拓扑和活动从权威事件/快照恢复；
- 不存在 UI 退出导致断网的副作用。

### 32.16 J-15：停止 node 但保留 WebUI

**前置条件**

- control 与 node 可独立监督；
- 用户已通过 Passkey 授权停止 node。

**用户流程**

1. 概览点击“停止节点”；
2. 系统显示正在停止；
3. node 释放 TUN、路由、Peer、Relay、Exit、Coordinator 职责；
4. control、WebUI、审计和配置服务继续运行；
5. 概览显示“已停止”，并保留“启动节点”主操作；
6. 用户可从 WebUI 重新启动 node。

**成功判据**

- 停止 node 不会关闭 WebUI；
- 路由、DNS、TUN 清理完整；
- 重启 node 后状态和网络成员关系可恢复；
- 停止过程中的失败有明确残留资源诊断。

### 32.17 J-16：全部 Passkey 丢失后的本地恢复

**前置条件**

- 节点 owner 的 Passkey 设备全部丢失；
- 用户仍能访问宿主机本地系统；
- 无可用远程恢复通道。

**用户流程**

1. 用户在宿主机以本地系统权限启动恢复命令；
2. 系统要求确认节点身份和恢复原因；
3. 系统撤销旧 Passkey 会话；
4. 用户注册新 Passkey；
5. owner ID 保持或按明确恢复流程重建；
6. 产生高风险审计事件；
7. 公网旧会话全部失效。

**成功判据**

- 不能通过公网、邮件、安全问题或管理员代操作绕过；
- 恢复不能泄露私钥；
- 恢复后旧设备无法继续登录；
- 恢复操作记录本地认证主体、时间、节点和原因。

### 32.18 J-17：多网络全局拓扑

**前置条件**

- 节点已加入多个网络；
- 各网络能力、颜色边界和可见性策略不同。

**用户流程**

1. 网络 → 我的网络，默认显示全局拓扑；
2. 每个网络以独立颜色虚线边界圈出成员；
3. 多网络节点只绘制一次，并位于交叠区域；
4. 选中共享节点，右侧显示各网络的成员关系、角色和能力；
5. 用户可按网络过滤、在列表和拓扑间切换；
6. 右键共享节点时显示允许操作的对象范围；
7. 涉及某个网络的操作必须明确网络上下文，不能误作用于全部关系。

**成功判据**

- 共享节点不重复绘制；
- 能力环、健康角标和网络边界可区分；
- 选择、筛选和批量操作跨视图一致；
- 网络隐私策略不会因全局视图泄漏敏感字段。

## 33. 权限矩阵

### 33.1 身份层次

必须先区分三个层次：

1. **节点所有者**：控制某台设备上的本地 node、文件、应用和密钥；
2. **网络身份**：节点在网络中的成员资格；
3. **网络治理角色**：网络 owner、管理员、普通成员、临时 Coordinator。

同一个人可能同时是多个身份，但任何身份都不能自动覆盖另一层。

| 角色 | 范围 | 核心权力 | 明确边界 |
|---|---|---|---|
| 节点所有者 | 本机 | 启停节点、选共享目录、限制本地资源、管理本机 Passkey | 不能绕过网络级拒绝 |
| 网络所有者 | 单个网络 | 最终治理、管理员任命、关键恢复 | 不能直接操作成员机器 |
| 网络管理员 | 单个网络 | 审批、成员、组、策略、Exit/Relay/File 授权 | 受 owner 约束，File 内容需显式授权 |
| 普通成员 | 单个网络 | 使用获准资源、管理自己的成员关系/本地规则 | 不能修改网络治理 |
| 临时 Coordinator | 单个网络中临时 | 维持运行、同步最后有效策略、协调连接 | 禁止治理写入、密钥变更和权限提升 |
| 发现访客 | 公共索引 | 查看公开签名资料、申请加入 | 看不到成员、拓扑、地址、策略细节 |
| 未认证公网访问者 | 公网入口 | 仅 HTTPS 登录/初始化页面 | 不能读取 API、状态或静态敏感资源 |

### 33.4 权限合成算法

一次操作必须同时通过：

1. 节点本地身份认证；
2. 网络成员资格验证；
3. 网络治理角色检查；
4. 目标对象 ACL；
5. 节点本地资源/隐私限制；
6. 业务状态和可用性检查；
7. 近期重认证要求（高风险操作）。

规则：

- 所有适用允许层取交集；
- 任意适用拒绝层立即拒绝；
- 网络拒绝不能被节点本地允许覆盖；
- 节点本地拒绝不能被网络管理员覆盖；
- 未知角色、未知策略、未知能力默认拒绝；
- UI 只做预判，服务端必须重新校验；
- 拒绝结果必须返回稳定错误码和可展示原因，但不得泄漏无权查看的对象存在性。

### 33.5 临时 Coordinator 的写权限冻结

临时 Coordinator 可以：

- 发布自己的临时期限和签名；
- 读取并同步最后有效策略；
- 协调已有成员连接；
- 触发健康检查和故障信息；
- 拒绝不一致或过期状态；
- 在正式候选恢复时移交。

临时 Coordinator 不可以：

- 增删成员；
- 修改管理员或 owner；
- 修改组、ACL、隐私和出口授权；
- 修改密钥、恢复材料或候选组；
- 删除审计；
- 把自己升级为正式 Leader；
- 代表网络签署新的长期成员资格。

## 34. 平台能力矩阵

### 34.1 声明规则

- 某平台只有在当前提交、目标硬件/系统版本和真实安装方式下有证据，才能标记“已验证”；
- 交叉编译通过不等于平台可用；
- 单元测试通过不等于 TUN、路由、Passkey、Exit 或服务托管可用；
- 桌面 GPUI 与移动端 Compose 不能互相替代验证；
- 平台不支持某能力时必须返回稳定“不支持”原因，不显示伪可用按钮；
- 同一能力在不同平台可有不同限制，但产品语义必须一致。

状态缩写：

- **V**：当前提交有明确测试证据；
- **I**：已有实现路径，但目标平台/真实环境仍待验证；
- **N**：当前没有完整实现；
- **P**：第一版目标，尚待开发；
- **—**：平台不适用或明确不提供。

### 34.3 Linux 当前边界

已有基础：

- Linux TUN；
- network namespace 端到端脚本；
- P2P/Relay/Exit 基础；
- GPUI 顶层入口；
- WebUI 服务；
- Criterion 数据面基线。

仍不能宣称：

- 已在真实第三方网络通过抗干扰测试；
- Google/YouTube 稳定可访问；
- 所有网络切换都能自动恢复路由和 DNS；
- 密码学 profile 已完成独立审计；
- 桌面 UI 已产品化；
- 关闭 UI 后 node 一定继续运行（当前 GPUI 生命周期与此冲突）。

### 34.4 macOS 当前边界

- utun 和路由代码路径存在；
- 需要 root/sudo 或相应系统授权；
- GPUI 实机、菜单、IME、文件选择和视觉未验证；
- Exit/Relay/Coordinator 需要目标硬件测试；
- 后台服务、系统扩展和权限模型尚未完成产品化；
- 不能根据 Linux 测试推断 macOS 可用。

### 34.5 Windows 当前边界

- WinTun 和 IP Helper 路径存在；
- 需要管理员权限；
- 驱动安装、升级、卸载和回滚未验证；
- 服务托管、Named Pipe 认证和防火墙体验未完成；
- GPUI 实机、DPI、IME、菜单和无障碍未验证；
- Exit/Relay/Coordinator 未达到 Linux 同级证据；
- 不能根据交叉编译结果宣称 Windows 可发布。

### 34.6 Android 当前边界

第一版目标：

- Kotlin + Jetpack Compose；
- 前台 `VpnService`；
- 共享 Rust 核心；
- Credential Manager 管理 Passkey；
- 包身份用于应用分流；
- 底部五模块导航；
- 不限制 Coordinator、Relay、Exit、File，由所有者显式启用；
- 显示电量、移动流量、后台限制和系统杀进程风险。

未完成前不得：

- 用桌面 WebUI 嵌入 Android 冒充原生应用；
- 宣称后台长期稳定；
- 隐藏系统限制；
- 因移动平台自动禁用全部网络能力。

### 34.7 平台能力发布门禁

一个平台要标记“支持某能力”，至少需要：

1. 当前提交构建；
2. 目标系统真实安装/启动；
3. 身份和权限流程；
4. 失败关闭与恢复；
5. UI 状态与错误展示；
6. 活动审计；
7. 升级/卸载清理；
8. 网络与性能报告；
9. 崩溃/重启测试；
10. 已知限制公开说明。

## 35. 页面状态矩阵

### 35.1 全局状态规则

每个页面都必须实现下列通用状态：

| 状态 | 页面行为 |
|---|---|
| 初次加载 | 骨架只表达布局，不猜测数据；显示可取消的加载状态 |
| 刷新 | 保留上一次权威快照，标记“刷新中”，不闪空页面 |
| 空状态 | 解释为什么为空，并给出唯一主操作或说明无可用操作 |
| 错误 | 显示稳定错误码、影响范围、重试和诊断入口，不显示虚假数据 |
| 无权限 | 说明缺少哪类角色/授权；可提供申请路径，不泄漏对象细节 |
| 平台不支持 | 说明当前平台不支持的能力和替代路径；控件禁用原因可见 |
| 降级 | 显示受影响能力、是否失败关闭和最近更新时间 |
| 维护/过渡 | 显示当前操作、operation ID、进度阶段和取消/禁止取消规则 |
| 陈旧数据 | 明确“最后同步于”，写操作禁用；不得把旧快照当实时状态 |
| 会话过期 | 保留页面上下文，要求 Passkey 重认证后继续，不丢失未提交编辑 |
| control 不可达 | node 可继续运行；显示控制服务异常，不谎报节点停止 |
| node 不可达 | 保留 control；所有依赖 node 的动作禁用并解释 |
| 离线 | 本地缓存只读；禁止乐观写入，出站改动必须等待权威确认 |

### 35.2 一级与对象页面

| 页面 | 空状态主操作 | 无权限/不支持 | 错误/降级重点 | 正常主操作 |

| 网络详情 → 概览 | 邀请成员或发布网络 | 管理操作按角色禁用 | 容量、能力、Coordinator、策略告警 | 处理问题或邀请成员 |
| 网络详情 → 成员与拓扑 | 邀请成员 | 隐私策略隐藏字段时解释 | 成员离线、连接质量、布局加载失败 | 选择成员、筛选、批量操作 |
| 网络详情 → 安全策略 | 从模板创建策略 | 无权查看时隐藏细节 | 冲突、拒绝优先、待应用差异 | 新建/测试/应用/回滚 |
| 网络详情 → 活动 | 无活动时说明事件范围 | 普通成员仅见自己可见事件 | 事件缺口、同步失败、审计保留策略 | 筛选、查看对象、导出授权范围 |
| 互联网出口 | 启用 Exit 或等待管理员授权 | 平台不支持 Exit、贡献义务未接受 | Exit 离线、撤权、DNS 泄漏、失败关闭 | 选择/测试 Exit、配置治理 |
| Relay | 启用 Relay 或等待授权 | 资源/权限不足时说明门槛 | 连通性、配额、Relay 故障回退 | 启用/限制资源/查看质量 |
| Coordinator | 指定候选组 | 临时 Leader 显示冻结权限 | 无多数、脑裂防护、入口切换、任期 | 管理候选组、查看选举 |
| File | 选择共享目录或等待授权 | 无 File 权限时不显示目录名 | 配额、路径安全、传输中断、撤权 | 浏览、上传、下载、继续传输 |
| 活动 | 扩大时间范围 | 审计级别不足时说明不可见范围 | 事件同步、保留周期、导出失败 | 筛选、跳转、导出 |
| 设置 | 选择基础配置组 | 平台不支持项显示只读说明 | 配置校验、证书、端口、代理、更新失败 | 保存、预览、导入、回滚 |

### 35.3 控件禁用原因

任何禁用控件必须能回答：

- 缺什么权限；
- 缺哪个前置状态；
- 是平台不支持还是当前节点未启用；
- 用户能否自行满足；
- 谁可以授权；
- 是否与网络策略冲突；
- 最近一次权威状态何时更新。

禁止使用无原因的灰色按钮、只有 Tooltip 的禁用按钮或点击后才提示“Unavailable”的伪控件。

### 35.4 空状态与搜索状态

- 空状态不等于错误；
- 搜索无结果必须保留筛选条件和清除入口；
- 首次为空应提供引导，不应展示模拟拓扑；
- 网络离线时不得保留旧在线成员并显示为“在线”；
- 无权限时不得通过数量、排序或页面闪烁泄漏被拒绝对象；
- 分页/虚拟列表不得在加载新页时清空当前选择。

## 36. 翻墙、网络质量与抗干扰实测口径

### 36.1 当前结论状态

截至本文审计，没有足够证据宣称：

- Google 在所有目标环境稳定可访问；
- YouTube 视频稳定播放；
- 抗干扰达到某个可量化等级；
- 吞吐、延迟、丢包达到具体数值；
- Linux/macOS/Windows/Android 已全部通过 Exit 实网验证；
- 密码学实现经过独立审计。

因此对外回答必须使用“未完成验证”或给出带环境、提交和时间的测试结果，不能使用“已经可翻墙”作为无条件的完成声明。

### 36.2 历史事故约束

此前在用户日常主机直接进行 TUN/路由测试曾导致断网，并留下需要手工 kill 的进程。该问题本身就是发布阻断缺陷，说明：

- 测试驱动缺少可靠的 finally/cleanup；
- 进程生命周期与 UI/测试套件耦合；
- 系统路由、DNS、TUN 的恢复不是原子操作；
- 测试环境与控制通道未隔离；
- “能启动”不能替代“能安全退出”；
- 让用户手工 kill 进程不是可接受的产品恢复路径。

任何新的实测必须证明失败路径也能自动清理，否则不得在真实主机运行。

### 36.3 测试环境拓扑

推荐最小环境：

```text
[测试客户端] ── 控制/测试管理网（独立于被测默认路由）
      │
      ├── Relay/Candidate Coordinator
      │
      └── Exit 节点 ── 外部目标站（Google/YouTube/测速端点）

[宿主机测试控制器] ── SSH/串口/带外控制 ── 所有被测节点
```

要求：

- 客户端优先放在 network namespace 或 VM；
- Relay、Exit、Coordinator 放在专用远程主机或隔离 VM；
- 管理面使用独立网卡、串口或带外通道，TUN 修改默认路由后仍能观察和控制；
- 外部目标与本地基线分别测量；
- 不使用用户日常办公主机作为第一个实网测试目标；
- 测试结束由控制器通过带外通道验证恢复，不依赖被测进程自报成功。

### 36.4 测试前快照

在隔离主机或明确许可的测试环境中，测试前至少记录：

- 默认路由、策略路由、IPv4/IPv6 路由表；
- DNS 配置、resolver 状态、搜索域和 DoH/DoT 设置；
- TUN 接口和链路状态；
- nftables/iptables/路由规则；
- 代理环境变量和系统代理；
- 相关 fuckipv6、relay、exit、测试辅助进程；
- 关键端口监听；
- 当前公网 IP、DNS 出口和目标连通性基线；
- 系统时间与时钟同步状态。

快照必须带哈希/时间戳并保存在测试控制器，而不是只存在被测节点本地。

### 36.5 硬超时与恢复

每次测试必须：

- 为启动、建连、路由切换、DNS 验证、吞吐和退出分别设置硬超时；
- 使用带外看门狗终止失控进程；
- 测试失败进入清理，而不是继续等待；
- 恢复默认路由、DNS、策略路由和接口；
- 校验无残留 TUN、nftables/iptables 规则和子进程；
- 恢复后重新访问控制通道和外部基线；
- 保存清理结果；清理失败时标为发布阻断，不生成“通过”报告。

### 36.6 功能验证矩阵

| 编号 | 测试 | 判据 |
|---|---|---|
| NET-01 | 未启用 Exit 时基线 | 直连 DNS/HTTPS/IPv4/IPv6 结果符合环境预期 |
| NET-02 | 启用 Exit 后 DNS | 只使用授权 resolver；无已知 DNS 泄漏 |
| NET-03 | Google HTTPS | 连续多次返回有效证书和成功 HTTP 响应 |
| NET-04 | YouTube 页面/媒体 | 页面内容可加载，媒体请求有实际字节进展 |
| NET-05 | IPv4 目标 | 路由、DNS、TLS 和响应链路正确 |
| NET-06 | IPv6 目标 | 有 IPv6 路径时验证；无路径时明确标记 skipped，不伪装 pass |
| NET-07 | 指定域名分流 | 命中规则走指定 Exit，未命中流量按规则直连或失败关闭 |
| NET-08 | 指定应用分流 | 应用身份正确，子进程继承，未知应用不被猜测 |
| NET-09 | 指定 IP/CIDR/端口/协议 | 命中顺序和最终路径与测试器一致 |

| NET-18 | Coordinator 故障 | 数据面不无条件中断，候选组接管 |
| NET-19 | 陈策略到期 | 失败关闭，不继续使用过期授权 |
| NET-20 | 长时间运行 | 24 小时无泄漏、无无界内存增长、无残留连接 |

### 36.7 抗干扰场景

必须模拟而不只等待真实审查环境：

1. UDP 丢包 1%、5%、20%；
2. UDP 乱序和重复；
3. 链路抖动和短时黑洞；
4. MTU 降低、路径 MTU 黑洞、接近 1280 字节边界；
5. IPv6 黑洞但 IPv4 可用；
6. DNS 超时、错误响应、污染式响应和 resolver 切换；
7. QUIC/UDP 被阻断，验证 Relay/TCP 控制路径的回退边界；
8. Relay 中途中止；
9. Exit 中途中止；
10. 默认路由切换和网络接口切换；
11. 睡眠/唤醒或进程被系统暂停；
12. Coordinator 被隔离；
13. 候选组多数不可达；
14. 网络分区恢复；
15. 证书/时钟异常；
16. 磁盘满、SQLite 锁竞争和审计写入失败；
17. 并发规则变更；
18. 进程被 SIGTERM、SIGKILL 和硬重启。

每项都必须记录检测时间、切换时间、恢复时间、用户可见状态和是否发生泄漏。

### 36.8 性能指标

最低采集：

- 吞吐：下载、上传、单流、多流、并发 1/8/32；
- 延迟：TCP/UDP RTT、p50/p95/p99、抖动；
- 丢包：本地观测与远端观测；
- 建连：DNS、TCP、TLS、Exit 选择和首个字节时间；
- 切换：Exit/Relay 故障后的检测与恢复时间；
- 资源：CPU、内存、文件描述符、线程数、连接数、TUN 丢包；
- 稳定性：24 小时内存/延迟/错误率趋势；
- 公平性：单流不会无限饿死其他流，多流资源有边界。

### 36.9 初始验收目标

以下是最低发布门禁，不是对所有网络环境的性能承诺：

- Google HTTPS：同一配置连续 5 次中至少 5 次成功，单次在定义超时内完成；
- YouTube：页面与媒体请求均产生真实字节进展；
- DNS：不允许出现未授权 resolver 的查询；
- 失败关闭：Exit 不可用或授权撤销时，不允许静默直连；
- 恢复：普通故障切换目标 ≤ 10 秒；测试结束后路由/DNS/TUN 恢复 ≤ 10 秒；
- 稳定性：24 小时无残留进程、无无界资源增长、无控制通道泄漏；
- 吞吐：同拓扑基线的 70% 以上；若环境基线本身不足，报告必须同时给出绝对值，不能只给比例；
- 延迟：直连 P2P 的 p95 额外延迟目标 ≤ 30 ms；Relay/Exit 路径必须报告绝对值，并按同路径基线比较；
- 丢包：无注入时稳定阶段 ≤ 1%；注入丢包时只要求正确降级/恢复，不伪造“无损”；
- 控制面故障：node 不中断，control 恢复后 10 秒内重新同步；
- UI 退出：0 次网络中断；
- 清理失败：0 次发布通过。

```bash

  --connect-timeout 10 --max-time 20 \
  --write-out 'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \

```

```bash
curl --fail --show-error --silent --location \
  --connect-timeout 10 --max-time 30 \
  --write-out 'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  --output /dev/null https://www.youtube.com/
```

约束：

- 不以 ICMP ping 作为 Google/YouTube 可访问证据；
- 不忽略 TLS 证书错误；
- 不把浏览器缓存、代理命中或服务端本地直连当作目标成功；
- 必须记录实际 Exit、DNS resolver、目标 IP/域名、时间、提交和网络环境；
- 必须至少进行一次冷 DNS 和一次已解析路径测试；
- 要验证视频时记录实际媒体分段字节，而不是只检查首页 HTML。

任何对外声明必须使用以下格式：

### 36.12 测试报告存储

- 机器可读报告提交到仓库的测试证据目录或 CI artifact；
- 报告中不得包含密码、Token、私钥、完整成员地址或用户流量；
- 截图可记录 UI 状态，但要脱敏；
- 每次发布引用具体 commit 和产物哈希；
- 失败报告与成功报告都要保留，不能只保留通过样本；
- 网络质量结论必须允许复核，不能用不可重现的单次口头测试替代。

## 37. 威胁模型与安全边界

### 37.1 安全目标

优先级：

1. 不泄漏节点私钥、Passkey、恢复材料和流量内容；
2. 不允许未授权成员获得网络治理或 Exit/Relay/File 资源；
3. Exit 不可用时不能静默直连或绕过管理员策略；
4. 公网 WebUI 不能被初始化竞争、会话窃取或 CSRF 接管；
5. Coordinator 分区时不能出现两个可写 Leader；
6. 恶意成员不能通过 File、发现记录或拓扑数据访问宿主机；
7. 控制面故障不能无故扩大权限或破坏已授权数据面；
8. 所有高风险操作可归因、可审计、可恢复。

### 37.2 资产

- 节点身份私钥、网络密钥、会话密钥；
- 所有者 Passkey 关联、初始化码和恢复材料；
- 网络成员资格、管理员授权和策略签名；
- Exit/Relay/File 能力与资源配额；
- 本机应用/进程、文件路径和诊断数据；
- 拓扑、真实地址和流量元数据；
- 审计记录、操作记录和配置；
- 二进制发布签名、更新包和 CI 凭据；
- 用户通过 Exit 访问的流量内容（系统设计上不采集）。

### 37.3 对手能力

| 对手 | 能力 | 主要目标 |
|---|---|---|
| 公网匿名访问者 | 扫描、暴力尝试、初始化竞态、CSRF、会话伪造 | 接管 WebUI |
| 被入侵的成员节点 | 伪造状态、扫描网络、重放、耗尽资源 | 越权或破坏服务 |
| 恶意网络管理员 | 修改策略、限制成员、查看被授权元数据 | 扩大控制或获取 File 内容 |
| 恶意 Exit/Relay 运营者 | 观察连接元数据、丢包、延迟、拒绝服务 | 流量分析或诱导泄漏 |
| 网络分区攻击者 | 隔离 Coordinator、制造多分区 | 脑裂、回滚或紧急权限滥用 |
| 供应链攻击者 | 污染依赖、构建、更新包 | 执行任意代码或窃取密钥 |
| 本机低权限进程 | 读取文件、调用本地 IPC、观察界面 | 提升本机或网络权限 |
| 文件系统攻击者 | 构造符号链接、路径竞态、超大文件 | 越出共享目录或耗尽磁盘 |

### 37.4 威胁与控制矩阵

| 威胁 | 主要控制 | 残余风险 |
|---|---|---|
| 公网首次认领被抢先 | 有效 HTTPS、一次性码、原子事务、限流、本地重置 | 码泄漏后、认领前仍有竞争窗口 |
| Passkey 钓鱼/设备丢失 | WebAuthn origin 绑定、多设备、近期重认证、本地恢复 | 用户主动批准恶意操作 |
| 会话窃取 | HttpOnly/Secure/SameSite Cookie 或受保护会话、短时 Token、CSRF、CSP、过期 | 终端被完全控制 |
| 反向代理伪装 | 明确可信代理列表、来源校验、TLS 终止约束、HSTS | 用户错误配置代理 |
| Exit 流量泄漏 | 失败关闭、IPv4/IPv6 同策略、DNS 路径校验、规则测试器 | 平台路由竞态或第三方应用绕过 TUN |
| DNS 泄漏 | 捕获/代理 DNS、DoH/DoT 策略、resolver 白名单、泄漏检查 | 应用自带硬编码 DNS |
| Relay/Exit 查看内容 | 端到端 secure-session、最小元数据 | 流量分析、时间/体积侧信道 |
| 恶意成员扫描 | 成员 ACL、速率限制、黑名单、最小拓扑可见性 | 合法成员滥用授权范围 |
| 管理员越权查看 File | 独立 ACL、角色不隐含内容权限、字段级隐私 | owner 主动错误授权 |
| 管理员操纵 Exit 路由 | 拒绝优先、节点本地拒绝、固定 Exit 限制、审计 | 网络级策略本身的合法但不当配置 |
| Coordinator 脑裂 | 单任期、候选组多数、持久化任期、fencing token、数据面不盲目服从旧 Leader | 网络分区长期无法恢复 |
| 紧急 Leader 自我升级 | 只读/运行权限冻结、签名限制、管理员阈值恢复 | 多数成员被同时攻陷 |
| 过期策略继续使用 | 签名策略 TTL、失败关闭、本地最后有效时间 | 时钟错误或长期离线 |
| 发现记录伪造/回滚 | 签名网络 ID、单调版本、过期时间、索引只作线索 | 索引拒绝服务 |
| 重放攻击 | secure-session 计数 Nonce、重放窗口、任期/会话绑定 | 窗口边界和密钥泄露 |
| File 路径穿越 | canonicalize、目录 fd/openat 类安全打开、符号链接拒绝、竞态检查 | 平台文件系统差异 |
| File 配额/DoS | 大小/数量/并发/速率配额、临时文件限额、断点状态认证 | 磁盘被授权用户合法写满 |
| 日志泄漏秘密 | 结构化脱敏、字段白名单、导出审计、日志轮换 | 崩溃转储含内存秘密 |
| 更新包被替换 | 签名校验、回滚保护、产物哈希、发布门禁 | 签名私钥被攻陷 |
| 本机 IPC 被冒用 | Unix Socket/Named Pipe 权限、进程认证、同用户边界 | 同用户恶意进程 |
| 依赖供应链 | 锁定依赖、审计、最小 feature、可复现构建、SBOM | 上游未知漏洞 |

### 37.5 控制面与数据面边界

- control 负责认证、策略、审计和操作编排；
- node 负责 TUN、路由、Peer、Relay、Exit 和 File 数据路径；
- control 异常不得自动关闭 node；
- node 异常必须让依赖动作失败关闭；
- node 对过期或无法验证的网络策略必须拒绝继续扩大权限；
- 已建立连接是否继续由最后有效策略明确决定，UI 不得自行延长授权；
- 临时 Coordinator 只能维持运行，不能改变长期授权；
- 任何“为了恢复而放宽策略”的方案必须被否决，除非有明确的多方恢复协议。

### 37.6 秘密生命周期

- 私钥优先使用操作系统密钥保护；
- Passkey 只保存凭据引用和公钥，不保存可导出的私密材料；
- 恢复码只在生成时显示一次，并存储在仓库之外；
- 初始化码短时有效、一次性、不可进入 URL/日志；
- 轮换密钥要有过渡期、旧密钥撤销和失败回滚；
- 诊断包默认脱敏，导出前显示包含的数据类别；
- 日志和测试夹具禁止包含真实 Token、密码、Cookie、私钥和完整远程凭据。

## 38. 数据模型、状态机与 API 契约

### 38.1 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `Node` | id, public_key, platform, version, created_at | 全局节点身份 |
| `NodeOwner` | node_id, credential_refs, recovery_state | 本机单一所有者 |
| `Network` | id, public_key, name, visibility, join_mode | 稳定签名网络 |
| `NetworkMembership` | network_id, node_id, state, joined_at | 节点与网络关系 |
| `RoleGrant` | network_id, subject, role | owner/admin/member 等 |
| `Group` | network_id, id, kind, selector | 自定义组/动态组 |
| `Capability` | network_id, node_id, kind, state, limits | Coordinator/Relay/Exit/File |
| `TrafficPolicy` | node_id, revision, default_action | 节点级有序规则集 |
| `TrafficRule` | id, priority, matchers, action | 首条命中 |
| `SecurityPolicy` | network_id, revision, subjects, resources, effect | 网络 ACL |
| `ExitGrant` | network_id, exit_node, groups, limits | Exit 使用授权 |
| `CoordinatorTerm` | network_id, term, leader, state, capabilities | 防止任期倒退 |
| `PeerLink` | network_id, endpoints, transport, health | 逻辑连接 |
| `FileShare` | network_id, node_id, root_ref, quota, acl | 共享目录 |
| `Operation` | id, kind, actor, target, idempotency_key, state | 写操作生命周期 |
| `Event` | seq, type, object, actor, time, severity | 权威事件 |
| `AuditEntry` | actor, local/network identity, action, result, reason | 不可静默删除的审计 |

数据库 schema 必须版本化。迁移失败不得留下半迁移状态；迁移前备份；旧快照可读取时也必须经过权限和签名校验。

### 38.2 节点状态机

```text
uninitialized
  → initializing
  → stopped
  → starting
  → running
  → degraded
  → stopping
  → stopped

running/degraded
  → failed

failed
  → recovering
  → running/degraded/stopped
```

约束：

- 不合法转移必须返回稳定错误码；
- UI 显示单一主状态，详细子状态放在诊断；
- control 状态与 node 状态分开存储，UI 合成唯一主状态；
- 进程启动成功不等于 node running；
- TUN/路由/权限失败不能被掩盖为 running；
- stop/failed 后必须执行资源清理并报告残留。

### 38.3 网络成员状态机

```text
discovered
  → applying
  → pending_approval
  → accepted
  → key_ready
  → connecting
  → active
  → degraded
  → leaving
  → left

pending_approval → rejected
applying → cancelled
active/degraded → suspended
```

成员在 `accepted` 之前不得获得网络资源。加入策略、Exit 贡献义务和隐私范围必须在 `applying` 前展示。

### 38.4 操作状态机

```text
queued
  → running
  → waiting_for_reauth
  → running
  → succeeded

queued/running
  → failed
  → cancelled
  → timed_out
```

规则：

- 写操作必带幂等键；
- 服务端生成 `operation_id`，同一幂等键返回同一操作；
- UI 不得在 `succeeded` 前修改权威状态；
- `failed` 必须返回错误码、可展示原因、受影响对象和重试建议；
- `cancelled` 不一定代表无副作用，必须报告已发生的部分变更；
- 多步骤操作必须返回阶段；
- 重连后先取快照，再按 cursor 补事件；
- 超时后通过查询操作状态确认，不重复盲目提交。

### 38.5 Coordinator 任期状态

```text
stable
  → election
  → leader_ack
  → stable

stable/election
  → partition
  → emergency_proposal
  → emergency_leader
  → handoff
  → stable

partition/emergency_leader
  → recovery_required
  → stable
```

每个 Leader 必须带：

- 网络 ID；
- 任期号；
- Leader 节点 ID；
- 候选组多数证明；
- 权限类别（full/emergency）；
- 签发时间和过期时间；
- fencing token。

成员拒绝低于当前任期的更新。旧 Leader 恢复后必须通过任期验证，不得直接覆盖新状态。

### 38.6 命令与事件建议

命令使用显式动词和对象：

- `node.start` / `node.stop` / `node.restart`
- `network.create` / `network.apply` / `network.leave`
- `membership.approve` / `membership.reject` / `membership.remove`
- `policy.test` / `policy.apply` / `policy.rollback`
- `traffic_rules.apply`
- `capability.enable` / `capability.disable`
- `exit.select` / `exit.revoke`
- `coordinator.candidates.update` / `coordinator.recover`
- `file.share.update` / `file.upload.start` / `file.download.start`
- `owner.passkey.register` / `owner.passkey.revoke`
- `certificate.reload`

事件使用过去时并带对象：

- `node.state.changed`
- `membership.state.changed`
- `network.policy.changed`
- `exit.path.changed`
- `coordinator.term.changed`
- `operation.progressed`
- `operation.completed`
- `activity.recorded`
- `snapshot.invalidated`

事件不得只发送字符串。建议结构：

```json
{
  "seq": 18422,
  "type": "operation.completed",
  "time": "2026-10-31T12:00:00+08:00",
  "operation_id": "op_...",
  "object": {"kind": "traffic_policy", "id": "..."},
  "actor": {"node_id": "...", "display": "..."},
  "result": {"status": "succeeded"},
  "revision": 12
}
```

### 38.7 HTTP/SSE 约定

建议路径：

| 路径 | 用途 |
|---|---|
| `GET /api/v1/snapshot` | 获取当前权威快照和版本 |
| `GET /api/v1/events?after=<cursor>` | SSE 事件流 |
| `POST /api/v1/commands` | 提交类型化命令 |
| `GET /api/v1/operations/<id>` | 查询操作状态 |
| `GET /api/v1/objects/<kind>/<id>` | 按权限读取对象 |
| `POST /api/v1/auth/webauthn/...` | Passkey 注册与登录 |
| `POST /api/v1/owner/recover` | 仅本地恢复通道 |
| `GET /api/v1/diagnostics/export` | 授权后导出脱敏诊断 |

要求：

- 远程 API 仅 HTTPS；
- 本地 IPC 使用相同语义但不同认证；
- 禁止通过 query string 传 Bearer Token；
- SSE 断线重连使用 cursor；
- 事件缺口或 cursor 过期时返回 `resync_required`，UI 重新拉取快照；
- 所有响应带 schema version、request ID、server time；
- 使用稳定错误码，不依赖自然语言做程序判断。

### 38.8 错误模型

```json
{
  "code": "permission.denied",
  "message_key": "error.permission_denied",
  "params": {"required_role": "network_admin"},
  "object": {"kind": "network", "id": "..."},
  "retryable": false,
  "recovery": {"kind": "request_access", "hint_key": "recovery.ask_admin"}
}
```

建议错误域：

- `auth.*`
- `permission.*`
- `validation.*`
- `state.*`
- `capability.*`
- `network.*`
- `coordinator.*`
- `exit.*`
- `relay.*`
- `file.*`
- `storage.*`
- `rate_limit.*`
- `internal.*`

错误必须能区分“暂时不可用”“无权限”“平台不支持”“依赖未就绪”“需要重认证”和“操作结果未知”。

### 38.9 审计与活动的关系

- 审计是安全/合规事实，覆盖命令、身份、对象、结果和原因；
- 活动是面向用户的解释层，可按重要性和隐私策略投影；
- 不是所有审计字段都能显示给普通成员；
- 原始 trace 不进入活动时间线，只在诊断中限时导出；
- 权限变更、出口变更、File 操作、Coordinator 任期、恢复和公网登录必须审计；
- 审计删除只允许按保留策略批量过期，不允许普通管理员单独抹除。

### 38.10 类型生成与漂移门禁

- Rust 领域枚举、命令、事件、错误和能力状态是源；
- OpenAPI/JSON Schema 由代码生成；
- TypeScript 客户端由 schema 生成；
- 生成产物进入版本控制或作为 CI 产物校验哈希；
- CI 检测生成文件是否与 Rust 模型一致；
- 不允许手写第二套命令枚举；
- Android 的 JSON 绑定也必须从同一 schema 生成或通过契约测试验证。

## 39. 视觉与交互规范

- 冷静、专业、可信，不追求视觉刺激；
- 中性背景承载信息，蓝色只表示可交互主路径；

### 39.9 右键/长按危险菜单

桌面：

- 菜单分区：查看/导航 → 常规操作 → 危险操作；
- 危险区与常规区之间使用间距和分隔线，不使用整块红色背景；
- 危险项使用危险色图标和明确动词；
- 不可逆项显示“无法撤销”；
- 立即执行，不再弹二次确认；
- 会话过期时先 Passkey 重认证，通过后继续原操作；
- 键盘菜单键打开，方向键移动，Enter 执行；
- 单键快捷方式不得绑定不可逆操作；
- 执行后显示本次 operation ID 和撤销入口（若有）；
- 右键未选中对象只操作该对象，右键已选中集合操作整个集合；
- 权限不足项不显示；部分对象无权限时显示影响数量和受阻原因。

移动端：

- 长按约 450 ms 打开底部 Action Sheet；
- 同一分区规则；
- 可用触觉反馈，但可在系统设置中关闭；
- 不可逆操作仍需明确危险标识，不能因移动端而添加隐藏确认步骤；
- 长按期间的滚动必须取消触发。

### 39.10 加载、刷新与布局稳定

- 初始加载使用与最终布局一致的骨架；
- 刷新保留旧数据并显示刷新状态；
- 禁止在每次 SSE 事件后整页替换导致滚动和焦点丢失；
- 拓扑保持节点位置，除非用户重置布局；
- 表格排序/筛选变化先显示 pending，再切换权威结果；
- 详情面板加载不得让主列表高度跳动；
- 空状态不显示假图表、假节点或假统计数据。

### 40.5 W2 生命周期验收

必须证明：

- 启动 UI 不隐式创建第二份 node；

- 关闭 UI 不调用 node shutdown；
- control 崩溃后 node 继续；
- control 重启读取 node 实际状态；
- stop node 不停止 control/WebUI；
- node stop 清理 TUN、路由、DNS、监听和子进程；

- 系统重启后按配置恢复服务。

### 42.2 已知残余风险

- 任何端到端加密都无法隐藏流量时间、体积和连接元数据；

- 管理员可能合法但不当配置策略；
- 用户设备被完全控制后，Passkey 和本地恢复都无法保证安全；
- 应用自带硬编码 DNS 或绕过 TUN 时，平台级分流可能不完整；
- Android 厂商后台策略可能终止前台服务；
- 网络分区期间治理操作必须暂停，恢复不是瞬时的；
- 1,000 节点以上拓扑需要额外聚合设计；
- 密码学实现未经独立审计前，不能宣称达到 WireGuard 或更高安全等级；
- 真实网络抗干扰没有永久保证，只能给出特定时间、环境和拓扑下的测试结论。

### 42.3 不应被误读为已完成的事项

- 11 页 GPUI manifest 存在，不等于产品 UI 完成；
- node manifest WebUI 存在，不等于旧 WebUI 已迁移；
- 类型化命令存在，不等于后端能力闭环；
- Linux Exit 代码存在，不等于 Google 可访问；
- Chromium/HTTP 测试通过，不等于所有应用流量正确；
- 拓扑可绘制，不等于治理和权限完成；
- File 基础传输存在，不等于 File 产品完成；
- README 能力表存在，不等于发布证据存在；
- 交叉编译通过，不等于目标平台可用；
- 单次连通，不等于抗干扰和稳定性合格。

## 45. 工程执行与提交约束

本节记录产品重构期间的工程纪律，防止“代码能用”与“提交可审计”脱节。

### 45.1 提交前检查

每次 Git 操作前：

```bash
git status --short --branch
```

必须先辨认并发修改和未跟踪文件，不得覆盖他人或前序工作的改动。

### 45.2 禁止提交的文件

以下路径在当前协作约束下绝对不得提交：

- `crates/client/src/cli/commands.rs`
- `crates/client/src/cli/mod.rs`
- `crates/client/src/webui/controller.rs`

即使功能测试通过，也不能把这几个路径混入提交。需要相关改动时，先与文件所有者/当前工作流确认，或保持未提交并明确报告。

### 45.3 secure-session 与 UDP 适配器提交顺序

若需要提交 secure-session 线格式/驱动和独立 UDP 适配器，必须按依赖顺序拆分为可独立构建、测试和审查的提交：

1. 共享线格式、类型、常量、测试向量和兼容边界；
2. secure-session 驱动接入及其单元/集成测试；
3. 独立 UDP 适配器及其队列、批处理、错误处理和资源上限测试；
4. 性能/故障注入文档与基线更新（如适用）。

要求：

- 前一项未通过时不得提交后一项；
- 每个提交自身可编译；
- 每个提交说明依赖关系和测试结果；
- 不得把禁止文件作为“顺手修复”混入；
- 不得 force push；
- 不得覆盖并发修改；
- 测试结果必须对应实际 commit，而不是工作区中未提交的组合；
- 完成后报告 commit hash、测试/clippy 结果、剩余未提交文件和阻塞项。

### 45.4 当前文档提交策略

本文是设计/决策文档，不自动代表产品功能完成。文档提交应与代码提交分离；若工作区存在大量并发修改，先确认文档是否为唯一预期变更，再提交。
