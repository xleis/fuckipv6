# 2026-11-13 宿主网络生命周期事故复盘

> 状态：已定位直接触发操作；底层生命周期缺陷仍待通过故障注入测试闭环。
> 影响范围：测试宿主机的全局代理、DNS 与新连接可用性。
> 处理原则：区分“直接触发”“故障加剧”“故障后的恢复动作”，不得颠倒因果。

## 1. 事故摘要

本次断网不是用户在故障后执行的 `sudo kill fuckipv6` 导致的。直接触发是一组针对正在使用的宿主机实例执行的
非原子“停止后重启”操作：

1. 先执行 `fuckipv6 down w12-hk`，主动移除正在承载流量的 TUN、路由和 DNS 接管；
2. 随后终止旧 `__control` 进程；
3. 使用不带 `--headless` 的 `systemd-run` 启动新实例，但新实例立即因 GUI 模式不可用而退出；
4. 失败后没有确认子进程树、DNS、路由和 TUN 已完整回滚；
5. 后续再次执行 `down/up`，并只对 `__node` 子进程执行 `kill -9`，进一步放大了生命周期失配。

因此，这是一次由**测试操作直接造成的宿主网络事故**，不能归因于用户后续的恢复命令。

## 2. 用户可见现象

- DNS 不可用，网页和微信等需要建立新连接的应用失败；
- START 云游戏仍可运行，但只能说明既有长连接尚未被立即中断，不能证明整机网络健康；
- `systemd-resolved` 持续对 `127.0.0.2` 报 degraded feature set；
- TUN、进程和 DNS 配置不再属于同一套完整的生命周期状态。

## 4. 根因与因果边界

### 4.1 直接触发

在用户正在使用的宿主实例上执行了非原子的 `down -> kill -> up` 手工重启。`down` 已经成功拆除了网络接管，
但替代实例没有成功建立，形成了“旧网络已拆、新网络未接管”的可用性空窗。

### 4.2 加剧因素

- 新实例以错误的 UI 模式启动，失败发生在接管完成前；
- 失败后未验证并终止整个 control/node 子进程树；
- 仅对 `__node` 执行 `kill -9`，不能替代 control 侧的正常清理；
- 重复执行 `down/up`，让 TUN、路由、DNS 和进程所有权更难对应；
- 未把 DNS 恢复、`systemd-resolved` 状态和真实新连接测试作为重启成功条件。

### 4.3 明确排除

- 用户在 02:20 执行的 `kill` 是断网后的恢复动作，不是原因；
- 本次操作没有修改或关闭路由器 OpenClash；
- 长连接仍存活不能证明 DNS、路由和新建连接正常；
- 局部命令返回成功不能证明整条数据面恢复。

## 5. 暴露出的工程问题

### 5.1 生命周期操作不具事务性

`down`、旧进程退出、新进程启动、健康检查和 DNS 切换不是同一个可回滚事务。任一步失败都可能留下部分状态。

### 5.2 进程退出不等于资源清理完成

control、node、TUN、策略规则、`/etc/resolv.conf`、`/etc/nsswitch.conf` 和本地 DNS 监听必须分别核验。
杀死单个子进程尤其不能作为生命周期管理手段。

### 5.3 DNS 配置是宿主高风险状态

`127.0.0.2` 是产品托管的 DoH 本地 DNS 地址。只要 `/etc/resolv.conf`、NSS 配置或
`systemd-resolved` 状态仍指向它，而对应监听已失效，就会出现“接口看似存在但 DNS 不可用”。

### 5.4 启动成功的定义不充分

进程存在、TUN 出现或 `status` 可查询都不足以证明启动成功。至少需要同时满足：

- 主进程和预期子进程树稳定；
- control IPC 可用，且只有一个生命周期所有者；
- TUN 地址和预期路由/规则完整；
- 托管 DNS 监听真实可查询；
- 通过 TUN 的 DNS、TCP 和 TLS 测试成功；
- 停止后 TUN、路由、DNS 和子进程全部恢复。

### 5.5 实机测试边界失效

在用户依赖的宿主全局网络上直接做破坏性生命周期测试，不是最小验证。测试隔离和回滚方案必须在执行前成立，
而不是失败后再寻找清理命令。

## 6. 后续必须遵守的操作红线

1. **禁止在共享宿主活动网络上直接做 `down/up/kill` 生命周期实验。** 优先使用独立 netns、容器或一次性 VM；
   测试实例不得接管宿主默认路由、宿主 DNS 或用户现有实例的 `/run` 锁。
2. **禁止把 `down -> kill -> systemd-run/up` 当作手工重启脚本。** 必须使用产品提供的单一、幂等、
   可超时和可回滚的生命周期入口；入口不存在时先实现并测试，不直接操作现网。
3. **破坏性操作前记录所有者。** 必须记录 PID/PPID、可执行文件、网络名、TUN、监听端口、`ip rule`、
   `ip route`、`resolv.conf` 符号链接目标、内容、NSS 配置和 resolver 状态。
4. **不得只杀子进程。** 停止必须从生命周期所有者开始，验证完整子进程树退出；`kill -9` 不是清理手段。
5. **失败即回滚。** 新实例未通过健康门禁时，不得保留其 TUN、规则、DNS 或孤儿子进程；必须恢复到操作前快照。
6. **DNS 恢复必须验证语义。** 除恢复文件内容外，还要恢复符号链接目标，并在需要时重启/刷新
   `systemd-resolved`；最后验证 `getent hosts`、TCP/TLS 新连接和目标域名访问。
7. **重启成功必须端到端判定。** 仅看到进程或 TUN 不算成功，必须验证控制面、数据面、DNS、出口路径和停止清理。
8. **不得修改或关闭路由器 OpenClash。** 用户明确要求保留其运行，除非收到新的明确授权。
9. **因果判断必须按时间线。** 先列操作和客观事件，再区分直接触发、加剧因素和恢复动作；禁止从最终残留倒推原因。
10. **长连接不是健康证据。** 游戏、IM 或既有 TCP 会话仍存活时，仍可能 DNS、路由和新连接全部故障。

## 7. 恢复顺序

事故后的安全恢复顺序应为：

1. 停止本轮新启动的全部实例，确认 control/node 子进程树退出；
2. 仅删除本轮拥有的 TUN、策略规则、路由表和监听；
3. 恢复 `/etc/resolv.conf` 的原始内容及符号链接目标；
4. 恢复 NSS 配置，按需重启 `systemd-resolved` 并清理缓存；
5. 验证 DNS、IPv4、IPv6、直连 TCP/TLS 和用户依赖的网络；
6. 记录恢复前后证据，确认没有把“恢复动作”误写成“事故原因”。
